# SSE 性能与重连约束

本文记录 2026-09-04 发现并修复的预警事件流阻塞问题，作为后续修改
`/api/v1/events`、活动告警快照和 SSE 客户端兼容行为的约束。

机器人端对应的读取超时、游标和节点快照规则见
[机器人 SSE 重连约束](../bot/docs/sse-reconnect-guardrails.md)。

## 已确认的根因

- `/api/v1/events` 返回 HTTP 200 后，首个 SSE 数据写入前会构建活动快照。
- 活动告警构建不能把 `reports=[]` 当作“没有报告”；这会回退到热报告集合。
- PostgreSQL 热报告默认最多 5000 条。一个 SSE 轮次不能对这批报告重复重算。
- `limit` 只限制输出数量，不能替代有界的快照生成。
- 全局 `IntelStore._lock` 内不得执行 PostgreSQL 网络 I/O、批量写入或提交。

## 当前实现保证

- 服务端在响应头后立即发送 `: connected`，让客户端能判断连接已建立。
- 活动告警、活动人员和 presence 状态按事件代次并以 1 秒 TTL 共享缓存；多个 SSE
  连接不能各自重新扫描完整热报告集合。
- 当前活动状态没有任何持久化报告来源 ID 时，活动告警必须直接返回空列表；presence-only
  告警由独立逻辑生成，禁止为了它加载热报告集合。
- OCR、presence 和过期处理只在全局锁内生成内存变更快照，PostgreSQL 写入使用独立
  的数据库写锁，不能重新放回 `IntelStore._lock`。
- 每次状态变更会递增事件代次并使缓存失效；heartbeat 变化同样必须通知事件流。
- SSE 首字节、缓存生成耗时和活动连接数属于必须持续观测的指标。
- `presence_` 开头的事件 ID 是由当前 presence 状态合成的，不对应持久化报告游标。
  客户端用它作为 `Last-Event-ID` 重连时必须直接通过 bootstrap 对账，禁止在发送响应头前
  扫描热报告或查询 PostgreSQL 历史记录。

## 禁止回归的修改

不要在 `_stream_events()` 循环中重新调用无界的
`_active_alert_list(..., limit=None)`，也不要把缓存快照改成每连接私有缓存。
不要把所有 `Last-Event-ID` 都无条件交给持久化报告游标解析；新增合成事件类型时，必须
明确其重连语义并添加“不触发报告扫描”的回归测试。
如需修改告警字段或游标语义，必须同时更新 API 文档、机器人测试和客户端联调说明。

## 客户端兼容要求

服务端可能先发送注释帧再发送 bootstrap。客户端必须把注释帧视为有效的连接活动，
并对连续无字节状态设置有限空闲超时；不能使用永久 `read=None`。
