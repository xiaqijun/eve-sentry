# SSE 性能与重连约束

本文记录 2026-09-04 发现并修复的预警事件流阻塞问题，作为后续修改
`/api/v1/events`、活动告警快照和 SSE 客户端兼容行为的约束。

机器人端对应的读取超时、游标和节点快照规则见
[机器人 SSE 重连约束](../bot/docs/sse-reconnect-guardrails.md)。

## 已确认的根因

- `/api/v1/events` 返回 HTTP 200 并写入 `: connected` 后，会在首个业务事件或 Bootstrap 前
  构建活动快照。
- 活动告警构建不能把 `reports=[]` 当作“没有报告”；这会回退到热报告集合。
- PostgreSQL 热报告默认最多 5000 条。一个 SSE 轮次不能对这批报告重复重算。
- `limit` 只限制输出数量，不能替代有界的快照生成。
- 全局 `IntelStore._lock` 内不得执行 PostgreSQL 网络 I/O、批量写入或提交。

### 2026-09-08：无游标重连首帧阻塞

星图无 `since` 或有效 `Last-Event-ID` 重连时，活动告警需要补齐持久化游标。旧实现的
`resolve_alert_stream_cursor()` 会为每条报告重新生成告警，间接进入评分和 zKillboard
网络请求。服务端虽然已返回 HTTP 200 和 `: connected`，但 bootstrap 会被外部请求阻塞；
客户端读取超时后再次重连，旧连接随之堆积为 `CLOSE-WAIT`。

标准告警 ID `evt_<report_id>` 与持久化报告是一一对应关系。游标解析必须直接读取报告的
`stream_position` 和 `report_id`，不得重新评分、查询 ESI/zKillboard 或生成告警。只有无法
直接映射的兼容事件 ID 才允许进入旧的完整匹配路径。此约束必须同时覆盖内存存储和
PostgreSQL 历史报告。

## 当前实现保证

- 服务端在响应头后立即发送 `: connected`，让客户端能判断连接已建立。
- 活动告警、活动人员和 presence 状态按事件代次并以 1 秒 TTL 共享缓存；多个 SSE
  连接不能各自重新扫描完整热报告集合。
- 缓存将事件代次、完成时间、水位、状态和报告游标索引封装成一个发布对象，构建完成后
  一次替换引用；发布后不得修改其内容。新鲜命中不获取构建锁，消费者的深拷贝在锁外进行。
  每个 store 只保留当前一份缓存，旧对象随使用它的读取者结束而回收。
- 同一时刻只有一个构建者。普通读取遇到正在刷新的过期或冷缓存立即返回未就绪；需要
  特定持久事件水位的读取最多等待构建锁 1 秒，仍未满足水位时禁止发送 Bootstrap。
  这只限制等待其他构建者的时间，数据库查询或 socket 写入自身的耗时仍须独立约束。
- 活动报告的 `evt_<report_id> → (stream_position, report_id)` 索引与状态来自同一数据库
  视图并一起缓存；无游标、时间游标和旧报告游标连接均复用该索引，禁止逐连接回扫热历史。
  索引只包含当前快照引用的报告，随快照整体替换，不累计历史或缓存未命中的 ID。
- 当前活动状态没有任何持久化报告来源 ID 时，活动告警必须直接返回空列表；presence-only
  告警由独立逻辑生成，禁止为了它加载热报告集合。
- OCR、presence 和过期处理只在全局锁内生成内存变更快照，PostgreSQL 写入使用独立
  的数据库写锁，不能重新放回 `IntelStore._lock`。
- 每次状态变更会递增事件代次并使缓存失效；heartbeat 变化同样必须通知事件流。
- PostgreSQL 必须在同一条 SQL 语句的一致视图中读取 active 条目、其引用报告和
  `MAX(intel_events.seq)` 水位 `W`；禁止先读内存 active、再单独查询水位。
- 从该视图构建告警时只能使用同批报告及其 `character_profiles` 元数据，禁止补读进程内
  人物缓存、resolver 磁盘缓存或触发写库；否则较新的身份状态会污染水位 `W` 对应的快照。
- OCR/ESI 丰富后的报告、active 条目、敌对波次和状态事件必须在同一个数据库事务提交，
  不能让丰富报告先于对应状态事件单独可见。其可变输入和 FIFO 票据必须在全局内存锁内
  冻结，等待票据及 PostgreSQL I/O 在锁外执行，数据库阶段不得回读 live active 字典。
- 所有状态事件事务在分配 `BIGSERIAL` 序号前取得同一个事务级 advisory lock，保证已提交
  序号形成前缀，不能让较高序号先提交并使恢复游标跳过较低序号。
- 事件历史清理可删除超过 14 天的旧行，但必须永久保留当前最大 `seq` 锚点，使数据库水位
  在长时间无新事件时仍保持单调，永久客户端 ACK 不会因 `MAX(seq)` 回退而卡死。
- SSE 固定本轮水位 `W`，按页完整重放 `seq <= W` 后才能发送 `state:W` Bootstrap；
  `seq > W` 留到下一轮。快照水位落后于持久事件或客户端游标时禁止发送 Bootstrap。
- 无游标、无 `since` 的首次 Bootstrap 直接锚定当前 `W`，不得把新客户端当成显式
  `state:0` 而回放整个 14 天保留日志；后续轮次从该水位继续。
- 多个 SSE 连接共享同一次快照构建；冷缓存锁竞争返回“未就绪”而不是伪造空状态。需要
  特定水位的等待也必须有界；缓存新鲜度在取得构建锁后重新判断，完成时间在构建完成后
  记录，避免慢查询阻塞所有连接或触发连续重建。
- SSE 首字节、缓存生成耗时和活动连接数属于必须持续观测的指标。
- `presence_` 开头的事件 ID 是由当前 presence 状态合成的，不对应持久化报告游标。
  客户端用它作为 `Last-Event-ID` 重连时必须直接通过 bootstrap 对账，禁止在发送响应头前
  扫描热报告或查询 PostgreSQL 历史记录。
- PostgreSQL 派生告警写出非状态 ID 后必须用无 `data` 的 `id: state:W` 控制块恢复原生
  EventSource 重连位置；解析器必须忽略该控制块，不能把它当作空业务事件。
- 标准 `evt_<report_id>` 游标解析只读取已持久化字段，不触发 `_alert_from_report()`、评分、
  ESI 或 zKillboard；回归测试必须用会立即失败的评分替身验证该保证。
- PostgreSQL 标准报告 ID 的初始恢复直接按报告 ID 读取持久化位置和时间，不先取得
  热报告锁；ISO 时间 ID 在报告解析之前识别，不能作为报告 ID 扫描历史。

## 禁止回归的修改

不要在 `_stream_events()` 循环中按连接重新调用无界的
`_active_alert_list(..., limit=None)`，也不要把缓存快照改成每连接私有缓存。持久事件后的
校准必须携带事件序号和数据库实际水位；禁止用所需水位冒充快照水位，也禁止逐连接重建。
不要把所有 `Last-Event-ID` 都无条件交给持久化报告游标解析；新增合成事件类型时，必须
明确其重连语义并添加“不触发报告扫描”的回归测试。
不要为了确认标准 `evt_<report_id>` 是否仍是告警而重新评分；事件 ID 到报告游标的映射是
持久化层职责，不依赖当前外部丰富结果。
如需修改告警字段或游标语义，必须同时更新 API 文档、机器人测试和客户端联调说明。

## 客户端兼容要求

服务端可能先发送注释帧再发送 bootstrap。客户端必须把注释帧视为有效的连接活动，
并对连续无字节状态设置有限空闲超时；不能使用永久 `read=None`。

客户端必须在本地状态中持久化最后一个已完整处理的 SSE `id`，重连时通过
`Last-Event-ID` 继续消费。不得仅依赖告警 ID 去重后从空游标反复拉取历史事件。
安全、告警和 bootstrap 事件只更新本地状态，不得逐事件强制同步心跳；心跳按固定间隔
节流，只有连接错误等状态转换允许立即上报。
