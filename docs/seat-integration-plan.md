# EVE Sentry 接入 GloryNavy_Seat（设计草案）

状态：2026-09-29。Sentry 端已落地密钥投影/吊销和 M1 业务认证切片；监控贡献、预警计费和双端对账仍处于设计阶段，不能视为已上线协议。

## 已确认的目标与现状

- `GloryNavy_Seat` 是本机的 Go/React 军团平台，采用 SeAT 风格模块架构；本方案不开发上游 PHP SeAT 插件。
- 平台成为监控和预警客户端密钥的统一创建、查看元数据和吊销入口；完整密钥仅在创建时显示一次。
- 提供有效监控可获得覆盖基础奖；独立核验通过的新敌情波次可另获监控事件奖。监控质量主要结合预警侧可核验反馈评估；使用预警按客户端收到的有效预警事件消耗果壳币，不按 SSE 在线时长收费。账本仍由平台的 `exchange` 模块负责。
- 哨兵继续负责截图/OCR、Presence、当前星系状态和 SSE；平台不复制实时敌情计算。
- 现有哨兵密钥只有 `desktop`、`service_readonly` 类型，没有监控/预警权限区分；平台已有可登记来源的果壳币流水和按比例自动兑换能力。

## 已落地：Sentry 端 Seat 服务接口（最小切片）

接口默认关闭。部署时在 Sentry 服务端配置 `EVE_SENTRY_SERVER_SEAT_INTEGRATION_TOKEN`，
长度至少 32 个字符；真实值只放在受保护的环境文件或密钥管理器中，不能写入仓库、文档、
响应日志或审计详情。启动参数对应为 `--seat-integration-token`。未配置时，下面两个接口
统一返回 HTTP 503 和 `code=seat_integration_disabled`。

接口只接受服务端 Bearer Token，不接受浏览器会话或普通设备密钥：

```http
POST /api/v1/integrations/seat/keys
Authorization: Bearer <seat-service-token>
Content-Type: application/json

{"operation_id":"00000000-0000-0000-0000-000000000001","key_id":"00000000-0000-0000-0000-000000000002","account_id":"00000000-0000-0000-0000-000000000003","name":"千珏监控","key_prefix":"seat_abcd","key_hash":"<sha256-hex>","permissions":["monitor","alert"],"protocol_version":1}
```

Seat 服务端负责生成明文密钥。Sentry 只保存 Seat 提供的 `key_hash` 和前缀，永远不生成或
返回另一把明文密钥：

```json
{
  "key_id": "00000000-0000-0000-0000-000000000002",
  "version": 1,
  "status": "active",
  "permissions": ["monitor", "alert"],
  "created_at": "2026-09-29T00:00:00+00:00",
  "idempotent_replay": false
}
```

使用相同 `operation_id + key_id` 和相同内容重试时返回同一记录（HTTP 200）；同一
`operation_id` 的内容（包括账号、前缀、哈希、权限或协议版本）发生变化时返回 HTTP 409、
`code=operation_conflict`。`key_hash` 必须是 64 位 SHA-256 十六进制值；完整哈希只进入
数据库字段，不进入响应、访问日志或审计详情。

```http
DELETE /api/v1/integrations/seat/keys/{key_id}
Authorization: Bearer <seat-service-token>
```

首次吊销和重复吊销都返回 `revoked=true`、`status=revoked`；未知 `key_id` 返回 HTTP 404、
`code=seat_key_not_found`。创建和首次吊销会写入 `auth_audit_log`，审计只记录集成名、
调用方 IP、请求 ID、操作 ID、账号 ID、密钥 ID、前缀、权限/原因和时间，不记录服务令牌、
明文密钥或完整哈希。

当前接口保存密钥生命周期和权限元数据；M1 另外提供独立的 Seat account 显式绑定和
业务 principal：绑定表不是 `auth_users` 的别名，provider=`seat` 下账号与本地用户一对一，
并保存 active/disabled 与 revision。`off` 表示 Seat 集成未启用，`enforce` 才按 `monitor`/`alert`
白名单放行；吊销、绑定禁用和本地用户禁用会推进授权代数，
主动结束对应 SSE。它仍未启用果壳币奖励、预警扣费或跨项目对账；那些能力完成前，Seat
端不得据此发放或扣除果壳币。

M1 的绑定由受信管理流程调用 `AuthService.bind_seat_account(account_id, user_id, actor)`，
冲突不自动合并账号、不改写历史归属；首次账号合并仍须由平台事务撤销旧 key 后重新签发。
Sentry 的客户端密钥创建入口已下线；业务 key 必须由 GloryNavy_Seat 签发、投影和吊销。
旧 desktop/service key 只保留管理/迁移用途，访问客户端白名单返回 `seat_client_key_required`。
业务 key 不允许访问 `/auth/*`、`/me/*`、`/admin/*` 或未列路径。

## 身份与密钥

平台账号 UUID 是成员归属的权威标识，不用角色名、QQ 号或单个 EVE 角色作为账本主键。一人多角色、换主角色不改变密钥与币归属；账号显式合并时，由新模块参与预览和同事务迁移。

GloryNavy_Seat 的 `sentry` 模块提供本人密钥列表、创建、吊销、监控贡献、预警消费及管理员审计。一个密钥可选择 `monitor`、`alert` 或两项；默认同时具备两项，以兼容当前客户端只有一个 API Key 输入框，也允许分别创建。权限不等于结算：监控按合格贡献获得奖励，预警只对已确认的有效事件收费。完整密钥仅在 Seat 创建成功时显示一次；Sentry 只保存投影，永远不提供本地客户端密钥创建入口。

哨兵逐请求校验用途：监控权限覆盖 detector 心跳、Presence、OCR、身份校验及监控所需读取；预警权限覆盖预警 SSE、局部星图及 alert 心跳。实际端点白名单应按客户端调用链逐项盘点，未知写接口默认拒绝，管理员接口永不开放给平台客户端密钥。机器人服务密钥继续独立管理。已发行的旧密钥在迁移期间照常工作，但不产生新奖励。

平台拥有密钥生命周期；哨兵保存本地验证所需的高熵随机密钥 SHA-256 哈希、平台密钥 ID、权限集合、状态和版本。两端通过专用内网集成接口创建、吊销和对账，不共享数据库，也不使用拥有全部管理权限的桌面密钥。

创建流程：平台服务端生成 `eve_` 密钥和操作 UUID，先记录 `creating`，只持久化哈希及前缀；向哨兵发送平台账号 UUID、密钥 ID、哈希、权限和版本。哨兵按操作 UUID 幂等写入本地验证表并确认，平台随后标记 `active` 并仅在当前响应显示一次明文。结果不明时不交付密钥，按同一操作 UUID 查询；仍无法确认则吊销可能存在的孤儿密钥，让成员重新创建。两端均不得在日志中记录明文或完整哈希。

吊销流程：平台先标记 `revoking` 并停止新的收益资格，立即调用哨兵；哨兵禁用密钥并主动断开对应 SSE 后确认。超时持续重试，页面显示待同步而不冒称已吊销。吊销是终态，不提供重新启用旧明文密钥；需要恢复时签发新密钥。接口使用专用轮换凭据、受限网络、操作 UUID、时间窗与请求签名或等效防重放；双方按版本定期对账，发现遗漏的吊销、账号禁用和归属变更。

哨兵本地验钥保持心跳、Presence 和 SSE 的实时性，不在每次请求时同步查询平台。平台定期下发带版本的完整有效密钥快照或增量水位，哨兵仅在成功核对该密钥仍有效后续租；平台暂时不可用时已同步密钥可在有限租约内继续使用。建议先以 30 分钟租约灰度并监控吊销积压，租约到期仍无法核对时拒绝该密钥的新请求并关闭其 SSE。这是可用性与吊销时效的取舍，跨服务吊销不具有瞬时原子性。成员只可管理本人密钥，管理员跨账号操作须留下审计。

账号合并由平台 `sentry` 模块参与现有 `MergeAccountTx`：预览包含密钥、待结算记录和未结预警预留的指纹，未结预留先结清或释放再合并；事务内迁移归属并保留首次 `original_account_id`。使用证据始终带不可变的密钥 ID，按发生时的账号归属分段，不能用密钥当前归属重写历史。合并后跨密钥去重；迟到记录入账前须锁活跃账号并复核合并映射。

## 监控贡献与预警质量证据

奖励按哨兵服务端接收时间计算，不接受客户端自报的累计秒数或本地时钟作为发币依据。预警端反馈用于评价监控质量，但不能用“有人收到预警”替代对监控贡献的归因。

- 监控：有效监控密钥下，detector 处于监控中、采集窗口有效，且服务端连续接收到 `source_status=active` 的 Presence；`0` 个敌对也是有效观测。仅启动按钮、心跳或 OCR 结果不足以计时。断帧超过建议的 20 秒、采集失效、密钥吊销或星系不在远程监控范围时停止计时；20 秒阈值需用真实采集间隔压测确认。
- 质量：记录监控覆盖/连续性、数据新鲜度、截断与采集异常、以及预警侧有独立依据的识别核验或误漏报反馈。每份证据须绑定实际贡献的 `key_id`、服务端认可的客户端、星系、事件/波次 ID、策略版本和修订版本；不上传截图或 OCR 原文到平台。现有事件只有部分 `primary_client_id`，没有可信的密钥归因和独立真值，因此质量加成和事件奖须等归因链与独立核验完成后才启用。无敌情或反馈不足的时段可获得基础覆盖奖励，不视为零质量；不按原始 OCR 命中数、预警接收者数或多开窗口数加奖。
- 同一平台账号、多监控设备和窗口的重叠秒数取并集，只选择一个有证据的贡献作为质量归因，不叠加分数。服务端断线、客户端离线、密钥吊销和采集失效均不计时。跨 UTC 日期与账号合并时点拆分区间，连接异常结束时只认最后一次有证据的短间隔。

目前 Presence/OCR 上传中的 `client_id` 主要取自请求体，监控贡献和预警质量归因前必须在服务端把它绑定到已认证 `key_id`，拒绝跨密钥冒用同一 `client_id`；记录被服务器采纳的主节点及其切换，而不是相信客户端自报贡献者。

哨兵按密钥、UTC 分钟持久化有效秒位图或等价区间（0–60 秒），同一记录修订时递增版本并追加使用事件。事件包含单调 `sequence`、不可变 `key_id`、UTC 分钟、区间/位图、版本和服务端时间。`sequence` 必须采用事务内分配的已提交前缀序号，不能直接把允许回滚留洞的 PostgreSQL `BIGSERIAL` 当作连续游标。平台按发生时的账号归属计算账号级并集，按 `sequence` 分页增量读取；按 `key_id + 分钟 + 版本` 幂等更新。消费游标、分钟重算、权益差额与币账写入同一平台事务，事务失败不推进游标。出现序号缺口或版本倒退时暂停该批并报警。

建议平台每分钟拉取，哨兵保留至少 30 天可重放事件，最终保留期按容量压测固定。平台停机后从游标补读；超出保留期进入人工核对，不能凭客户端补报造币。此链路异步运行，不阻塞 Presence 接收和 SSE 推送。

平台分别将 `sentry_monitor`（覆盖基础奖）和 `sentry_monitor_event`（核验波次事件奖）注册为固定奖励来源，两者独立开关；预警是币消费，不得伪装成负奖励或兑换订单。浏览器不能直接提交时长、质量分或金额。`sentry` 模块拥有证据和权益表，通过宿主注入的窄事务回调调用现有 `exchange.ReconcileTx`，不直接改币账。质量权重、最低反馈样本量及加成范围均须版本化；现有 `ReconcileTx` 的首次兑换费率冻结机制不能保证迟到证据采用发生时费率，正式发币前须增加受信来源的费率快照契约。币的最小单位仍为 0.01。

同一账号/UTC 日/费率版本使用稳定权益引用，累计有效秒和质量权重后再做整数换算，避免逐分钟舍入损失。日内调价开启新引用，旧权益不重算。每日上限、启停时间和费率构成策略版本；结算事务锁定策略版本与来源比例，按当天时间顺序先应用总上限，再把合格秒数分配给各版本。只有启用时间之后的有效秒数进入可兑换权益；此前只读观测不自动补发。证据更正导致时长减少时按原比例负向冲正，已消费时沿用现有欠额规则。账号合并不重新计时或兑换，保留原流水与首次归属。

事件奖以服务端稳定 `wave_id` 为单位，只有独立证据或人工复核确认的新敌情波次进入候选。哨兵须输出波次起止、分段/去抖策略版本、核验状态与修订、独立核验引用、首次有效发现时间，以及每个合格贡献的监控 `key_id`、已认证 `client_id`、星系、采样/确认时间、采集健康、识别质量和实际被采纳的主节点/交接证据。单帧抢报、同设备反复上传、画面截断和自行评价不能构成事件奖。多个节点若分别提供可核验的发现、确认或名单补全，可按其真实贡献进入候选；不能只凭 `primary_client_id` 或客户端自报名单分配。

平台按波次发生时的账号归属去重，同账号多密钥只占一个贡献名额，再按版本化的及时性与质量规则分配**一个固定总奖励池**；所有账号份额之和不得超过池额，不是每个客户端各领一份。未达到独立核验或归因要求的波次暂不发事件奖；是否有预警用户付费接收，与监控者获奖无关。权益引用按 `wave_id + 事件奖政策版本 + 原归属账号` 稳定记录；波次撤销、误报或贡献归因修订时，哨兵追加证据修订，平台按原引用差额冲正，不删除旧流水。池额、分配规则和每日账号上限待配置，默认关闭事件奖。

服务端证据可证明“持有有效密钥的连接在持续上报”，无法从网络侧证明画面真实或预警被真人阅读。上线初期应采用低额每日上限、已绑定 EVE 角色校验、异常并发设备审计；不能把客户端自报的 `monitoring=true` 直接当成发币证明。

## 按有效预警事件扣费

当前 `intel_events` 有 `state:<seq>` 可恢复状态游标，`hostile_waves` 有内部 `wave_id`；但 SSE 的 `alert.entered`、`alert.updated`、兼容报告告警、`bootstrap` 可能描述同一次来敌，`state:<seq>` 是变更序号而非收费事件 ID。新协议须定义不可变的 `charge_event_id`（建议绑定持续稳定的波次/事件，不因名单修订、重连或多端接收而变化）、修订版本、生命周期、服务端过滤/抑制结果和撤销原因。默认仅“新进入且符合已启用规则的来敌事件”具备收费资格；人员补全、名单更正、状态更新、清空、历史重放和 bootstrap 不另收费。若希望同波次后续新敌人单独收费，须先另行明确业务规则。

现有 SSE 的 `min_score`/`min_level`、全局星图范围及客户端本地范围/静音/冷却并非统一的用户收费规则；尤其持久状态事件与兼容报告告警走不同路径。收费前须把“该账号订阅哪些星系/等级、什么情况抑制”的策略及版本放在服务端统一判定，并在发送记录中固化判定结果。客户端本地可以再拒收，但拒收后不应确认或扣费。

收费资格必须依次通过四关，哨兵对每关保留带规则版本和原因的服务端证据，平台只核对并结算：

1. **来源有效**：产生来敌的监控密钥在采样时有效，采集窗口健康，作为本次判断依据的 Presence/OCR 样本新鲜，星系位于允许的远程监控范围；客户端自称在线、心跳存在或历史截图均不足以通过。
2. **识别可信**：敌对识别达到版本化置信阈值，且有连续有效采样或独立证据复核。单帧噪声、截断/异常画面、无法归因的识别先标记待确认，不进入收费投递；不能因为同一客户端重复上报就当作独立复核。
3. **事件有效**：服务端形成新的稳定 `charge_event_id`/波次，并通过该成员的预警规则；被过滤、抑制、去重、重放或撤销的事件不具收费资格。同一波次的人员补全、状态更新与清空不新增收费事件。
4. **软件确实收到**：存在账号级未过期的预付额度、哨兵的发送记录，以及客户端 UI 处理后的幂等 ACK；任何一项缺失都不能最终扣费。ACK 仅证明软件处理，不证明真人已阅读。

四关状态建议区分 `candidate`、`pending_review`、`eligible`、`delivered`、`confirmed`、`revoked`，每次判定/复核以修订事件追加而非覆盖原记录。独立复核或成员申诉认定误报后，哨兵按原 `charge_event_id` 发布撤销及依据，平台按原扣费引用退款；不声称算法能绝对证明游戏内真相。置信阈值、连续采样间隔、独立复核渠道、申诉和退款时限均待业务确认并版本化，不由客户端单方决定。

为避免多帧确认拖慢来敌提醒，首帧可立即发送明显标注“待确认”的免费提示；后续通过四关后，只有再次向客户端投递明确标注为收费的正式事件并收到 UI ACK 才结算，不能对先前免费提示追溯扣费。待确认提示与正式事件复用波次关联，正式事件仍按同账号同 `charge_event_id` 最多收费一次。

现有 `ack_alert` 修改报告的 `acknowledged_at/by/note`，含义是业务上的人工确认，不是客户端交付 ACK，绝不能复用为收费凭据。现有 `intel_events.seq` 是 PostgreSQL `BIGSERIAL`，即使写事务用 advisory lock 串行，回滚和清理仍可能造成数值缺口；新的结算流水应使用可核对的提交水位与保留期边界，不能直接要求该旧序列永远连续。

仅服务器 `wfile.flush()` 成功不能证明客户端已收到，更不能证明用户已阅读。新客户端必须在完成本地接收、规则核对、去重并投递 UI 后，以 `key_id + connection_id + charge_event_id + revision + delivery_id` 调用有幂等键的接收确认接口；服务端核对该连接确实发送过对应有效事件，再形成不可变送达记录。现有客户端先在 worker 中把 ID 写入本地 `seen_alert_ids`、随后异步发 UI 信号，UI 还可能因本地范围设置丢弃，不能直接把这一步视作已送达。没有客户端确认、超过确认期限、旧客户端、免费流或被抑制事件均不扣费；确认也只证明软件处理，不证明真人阅读。

预警扣费必须先在平台 `exchange` 按秒数冻结币额，再给哨兵签发绑定账号、价格版本、`unit_seconds`、`unit_price_minor`、`reserved_seconds` 和有效期的授权。哨兵须在数据库内按账号原子占用有效预警区间的 `duration_seconds`，同一 `charge_event_id + revision + started_at + ended_at` 多设备重收只占一次；未确认在超时后释放占用，已确认消耗区间，撤销或误报按原区间引用退款。平台按 `ceil(duration_seconds / unit_seconds) * unit_price_minor` 计算金额并以唯一区间引用结算；对账不明时继续占用而非先退款。断网只能消耗尚有效且已冻结的秒数，不能无限追欠或重复收费。平台 exchange 现有 `Spent` 面向兑换订单，正式扣费前需新增受信服务的预留、消费和退款账本契约。

## 两端对账：哨兵侧承诺

两项目不共享数据库，也不假定跨库事务。哨兵是**实际验钥状态、已采纳监控区间、波次/贡献及核验修订、预警发送与客户端收件确认**的事实源；平台是**账号归属、奖励/收费政策、币预留与流水**的事实源。哨兵不接收平台币余额、不自行算果壳币；平台不能凭自己的页面状态推断哨兵已吊销密钥或已交付预警。双方所有创建、吊销和授权操作以持久 `operation_id` 幂等重试，明确区分“请求已发出”“哨兵已提交”“平台已入账”。

| 对账对象 | 哨兵提供的核对键与事实 | 差异处理边界 |
| --- | --- | --- |
| 密钥 | `operation_id/key_id/version`，实际权限、账号投影、状态、吊销确认时间及租约水位 | 同一操作可查询/重放；哨兵不会因平台请求超时就假称创建或吊销成功。吊销未同步显示差异，超过约定租约后拒绝未知或已吊销密钥的新请求并关闭 SSE |
| 监控与质量 | `key_id + UTC 分钟 + revision`、秒级区间、质量证据 ID/修订、贡献节点及星系 | 哨兵只提供已采纳事实和更正，不提供“应得币额”；缺帧不补造、迟到修订追加而非覆盖历史。平台逐秒去重及按原权益引用计算差额 |
| 核验波次事件奖 | `wave_id + 核验版本`、贡献证据 ID 与 `key_id` | 哨兵给出完整波次及贡献修订，不计算奖励池或份额；归因/核验不完整时标记待确认。平台按账号去重、固定池额和原权益引用核对，误报按原引用冲正 |
| 预警与授权 | `grant_id + account_id + charge_event_id + revision + started_at + ended_at`、`delivery_id`，资格/规则版本、发送、收件 ACK、撤销及秒数占用 | 哨兵按账号原子占用，不超出 `reserved_seconds`；无 ACK 不标记消费。状态不明保留占用等待核对，不因一次空页就释放；平台按唯一区间引用结算或退款 |

哨兵新增受限、只读的分页事件接口，分别暴露密钥操作结果、监控区间/质量修订、核验波次与贡献修订、预警授权/投递/ACK/撤销。每页返回稳定排序的事件、`next_cursor`、`committed_watermark`、`earliest_available_watermark`、`has_more` 与快照/协议版本；游标只覆盖已提交的完整前缀，未提交事务绝不提前发布水位。分页期间的同一水位须可重复读取，重放返回相同不可变 ID 和修订；晚到更正以新事件追加。现有 `intel_events.seq BIGSERIAL` 不能直接充当该结算水位。若请求游标早于最早可读水位，哨兵显式返回不可恢复缺口，不返回看似正常的空页。

另提供按 UTC 日监控证据、按波次核验/贡献、按授权预警投递的记录数、最高修订和规范化摘要，便于平台与已镜像明细交叉核验；摘要算法、字段排序、空集合表示及版本须冻结，摘要不取代明细。建议平台每分钟拉增量、每 15 分钟核对近期日/波次/授权、每日复核最近 48 小时；哨兵为此保留可重放记录及明确的保留期水位，实际节奏和容量在联调压测后确定。尚未闭合或仍可修订的窗口应标记“待对账”，不能把当前零条当作最终零条。

自动修复只允许同一操作的幂等重放、可证明的漏拉补读、已核验修订造成的差额/退款。版本倒退、归属冲突、超过保留期的缺口、ACK 与平台币账相矛盾时，哨兵保留原始事实并发出差异告警，平台暂停相关账号、日期或授权的新结算，由管理员核验；两端均不静默删除或改写历史流水。对账记录保留双方水位、差异类型、首次/最近发现时间、重试次数及处理人。

## 本轮 Sentry 协议底座（v1，未启用生产扣费）

Sentry 已增加 SQL 持久化的 `seat_alert_grants`、`seat_alert_events`、
`seat_alert_deliveries` 和 `seat_alert_consumptions`，以及对应的 Seat 集成 API：授权创建/撤销、
收费事件修订、投递预留、客户端 ACK、事件游标和投递/消费游标读取。`--allow-alert-consumption` 默认关闭；
关闭时授权预留、投递和 ACK 返回 `alert_consumption_disabled`，不会占用额度。开启测试开关后，
同一 `operation_id`、同一 `charge_event_id + revision`、同一 `delivery_id` 和同一授权下的
重复事件分别按规范化请求哈希幂等；同一账号多设备重收只创建一条
`grant_id + charge_event_id + revision + started_at + ended_at` 预留。ACK 必须绑定已发送的 `delivery_id`、Seat `key_id`、账号、
连接、事件修订和幂等键，成功后才把 `reserved` 变成 `consumed`。

这部分只保存 Sentry 事实和平台价格快照，不调用 GloryNavy_Seat exchange，不计算或写入币账，
也不会自动把现有 SSE `alert`/`state:<seq>` 当成收费事件。收费事件的资格四关、生产费率、
预留期限、未确认释放、撤销退款、对账任务和新客户端消费者标记仍需与 Seat 当前 Goose 58
接口完成联调后再冻结；在此之前不得把测试开关、事件 API 或文档字段解释为已上线收费能力。

平台新页面 `/sentry` 提供“我的密钥”“监控覆盖/核验事件收益”“预警额度与消费”，管理员另见密钥异常、对账滞后、两类监控奖励政策和预警单价/限额。成员只查看本人；管理员查看他人仍逐次检查当前管理员身份。果壳币余额与流水沿用 `exchange` 页面，仅增加来源和扣费类型标签。固定文案走平台的 `msg` 中英文词表，页面按统一模块声明注册。

| 方向 | 职责 | 约束 |
| --- | --- | --- |
| 平台 → 哨兵 | 创建、查询、吊销平台密钥 | 专用服务身份、操作 UUID、版本、幂等和脱敏审计 |
| 平台 → 哨兵 | 批量密钥对账 | 分页、状态版本水位，绝不回传明文 |
| 平台 ← 哨兵 | 按游标读取监控区间、质量/波次贡献修订与预警送达/撤销事件 | 连续提交水位、有界分页、保留期、修订版本和缺口信号 |
| 平台 → 哨兵 | 发放/撤销预警秒数授权 | 账号、价格版本、`unit_seconds/unit_price_minor/reserved_seconds`、到期时间、操作幂等；断网不得超额 |
| 客户端 → 哨兵 | 确认收费预警接收 | 绑定已发送的连接/投递/事件 ID；幂等、限时、不可凭空确认 |
| 浏览器 → 平台 | 本人密钥、使用、收益及管理员配置 | 本站会话、CSRF、对象范围和操作审计 |

最低契约数据：密钥操作需 `operation_id/key_id/account_id/permissions/version/status`；监控证据需 `sequence/key_id/client_id/system_id/UTC interval/capture_health/quality_evidence_id/revision`；核验事件奖需 `wave_id/system_id/start_at/end_at/segmentation_policy_version/verification_status/verification_revision/independent_review_ref` 和每个贡献者的 `key_id/client_id/first_valid_detected_at/accepted_samples/quality_evidence_id/contribution_revision`；收费事件需 `charge_event_id/wave_id/revision/event_type/system_id/rule_version/eligibility/revocation_reason`，并附来源健康、识别置信/连续采样或独立复核引用、四关判定结果与复核版本；预警投递/消费需 `delivery_id/connection_id/key_id/account_id/grant_id/charge_event_id/revision/started_at/ended_at/duration_seconds/ack_deadline_at/sent_at/ack_at/state`；授权需 `grant_id/account_id/price_version/unit_seconds/unit_price_minor/reserved_seconds/remaining_seconds/expires_at/status`。所有增量接口须给出游标、提交水位、最早可读水位、分页上限和修订语义。上述仅为拟定字段，冻结前需双方共同确认并写入 API 文档。

客户端继续使用现有服务器 URL 与一个设备密钥输入框。收费预警 SSE 需要明确的消费者标记，并由服务端按密钥权限及剩余额度核对；旧客户端未携带标记及接收确认时不得收费。新接口路径、字段、错误码和版本在实现前写入两仓 API 契约。

## 发布顺序与验收

1. **兼容服务端**：先发布哨兵密钥投影、用途校验和集成接口；旧密钥可用。验证重复创建、结果不明、吊销、SSE 断开、权限越界和跨用户 `client_id`。
2. **平台管理**：发布平台 Goose 迁移、`sentry` 模块、合并参与方、页面和同步任务，仅测试账号领新密钥。切换管理入口后，哨兵原桌面密钥创建功能全部下线；历史 key 仅保留兼容认证和迁移审计用途，避免双入口继续发行。
3. **只读证据**：哨兵发布监控区间、质量/波次贡献修订、预警事件/接收确认的游标接口，平台先只读对账至少一晚，不发币也不扣费。核对空敌对图标、多个窗口、代理关闭、SSE 正常重连、跨日、波次闪断合并、过滤与重放。
4. **监控奖励灰度**：登记 `sentry_monitor` 与 `sentry_monitor_event` 两个独立来源，发放开关默认关闭；先实现费率快照，再仅对测试账号配置覆盖奖励、事件池额/分配规则、上限和生效时间。先验证基础覆盖奖，再验证独立核验、可信归因、账号去重、池额不超发、误报冲正和不依赖预警购买，随后分别开启生产发放，不追溯灰度前时段。
5. **预警扣费灰度**：平台 exchange 完成服务预留/消费/退款后，哨兵实现秒数授权、账号级原子占用及接收确认；新客户端发布消费者标记和确认协议。验证无余额、多端重复、重连、超时、断网、撤销、补偿和合并，再仅测试账号开启收费。旧客户端在兼容期可继续免费使用，但不形成收费确认。

回退时先停用 Seat 新发放与投影同步，保留本地验钥和历史 key 的迁移兼容。产生新密钥、使用事件和币流水后，不得直接回退到不认识新结构/来源的程序或删除迁移；先停后台任务、核对游标和待吊销操作，再切兼容版本。两仓生产发布分别遵守各自受保护流程。

验收至少覆盖：完整密钥只显示一次，成员不能管理他人密钥，吊销后新请求拒绝且 SSE 断开；无密钥、旧密钥及重复设备不发币；两台设备同时运行不翻倍；断线和采集失败不计；平台停机补读不重复；日内调价不重算旧权益；负向冲正、账号合并和重放保持账本一致。事件奖还须证明同波次总份额不超过固定池额、同账号多开不翻倍、单帧抢报/未核验不发奖、误报按原引用冲正且与预警接收者数量无关。收费须证明仅已授权、已发送、客户端已处理且未撤销的有效区间按秒结算，bootstrap/更新/清空/旧客户端/未确认均不扣，秒数不足或断网时不会超额。

## 与 19:19 断连的关系

2026-09-21 19:19，Clash Verge 停止本机代理核心后，哨兵客户端仍尝试该代理，产生 `WinError 10061`；114 服务端同期正常。客户端网络层应为哨兵服务地址提供明确的“直连/系统代理”选择，并在代理配置变化后重建 HTTP opener。此修复单独验证；代理中断期间没有服务端证据的时段不补算收益。

## 待确认的业务规则

- 监控每有效小时基础奖励、质量加成条件/最高权重、最低反馈样本量、每日上限与人工复核规则。
- 核验波次事件奖的固定池额、合格贡献与及时性/质量分配规则、账号每日上限、独立核验渠道及波次闪断合并阈值；未冻结前保持事件奖关闭。
- 预警有效区间的 `unit_seconds/unit_price_minor`、每次冻结 `reserved_seconds` 及期限、接收确认超时、被判无效后的退款时限；是否同一来敌波次同一区间只结算一次（本方案默认是）。
- 收费识别的置信阈值、连续有效采样的间隔与次数、可接受的独立复核渠道、申诉时限；在这些规则冻结前不启用正式扣费。
- 是否只给 Web 配置的远程监控范围发监控奖励；本方案默认仅此范围，本地预警模式不算监控收益。
- 旧哨兵密钥是否由成员重新领取，还是允许一次性迁移其归属；默认不自动迁移，也不补发历史币。
