# 人员档案刷新模拟压测（2026-09-11）

## 结论

当前实现可以在几十万条过期档案积压时优先刷新当前人员，但不能据此承诺
50 万份档案每小时全部刷新一次。本次 50 万组短时吞吐约 98 人/秒，
按相同吞吐线性推算一轮约 85 分钟；一小时完成 50 万至少需要平均 139 人/秒，
还未计入重试、身份补查、联系人刷新和其他业务负载。

本次只增加压测脚本、脚本测试和本报告，未修改业务实现，也未访问生产或官方 ESI。
GitNexus 调试查询辅助定位刷新链路；索引有滞后，结论以当前源码和实际运行指标为准。
压测脚本安全测试及档案、运行时、过期队列、旧资料刷新相关回归共 76 项通过（42.42 秒）。

## 方法与边界

- 基线：`538f53934acdfa6534b629b268448f39c3e02d96`。
- 本机 Windows 11，i5-9400F，6 个逻辑处理器，约 16 GB 内存；Python 3.13.9。
- 独立本机 PostgreSQL 16.14，`127.0.0.1:55440`；每组使用随机、独立 schema。
- PostgreSQL `shared_buffers=128MB`、`work_mem=4MB`、`fsync=on`、`synchronous_commit=on`。
- 与当前控制器一致的连接池：最小 1、最大 8，连接等待 2 秒；SQL 超时 5 秒、锁等待 2 秒。
- 调用真实 `PersonnelArchive` 和 `PersonnelRuntime`，保留每批 100 人、后台调度、
  维护扫描、共享请求间隔、逐人落库及内部通知回调；只替换 ESI 客户端为内存模拟。
- 每组真实创建全部人员档案、姓名索引、1000 个军团、100 个联盟，以及每人两条任务：
  一条已过期归属刷新、一条未过期姓名刷新。归属已过期约一小时，P2～P5 均匀分布。
- 模拟每次归属请求耗时 200 毫秒，总是返回成功数据及一小时有效期；无真实 HTTP。
- 每组采样 45 秒，期间三波、每波 10 个已知身份且归属过期的人员提升为当前人员。
  延迟从 `set_active` 前计时，到内部回调确认新获取的归属资料为止。
- 吞吐按测窗结束前的 `refresh_success / 实际测窗秒数` 计算；停止时在途任务另行收尾。
- 仓储调用耗时包含连接池等待、SQL 和事务；计时包装器本身也有少量开销。

**不是完整刷新 10 万、30 万、50 万人的长跑测试。全量耗时是短时样本外推，不是实测。**

以下未覆盖：真实 ESI 限流/超时、47 Gateway CPU/内存、114↔47 网络限速与序列化、
姓名首次解析、联系人刷新、历史导入、OCR 上报、SSE、QQ 投递，以及持续一小时后的再次过期。
内部回调延迟不能当作客户端或 QQ 的端到端延迟。

## 实测结果

| 人员数 | 任务数 | 表及索引大小 | 测窗成功刷新数 | 吞吐（人/秒） | 全量一轮外推 | 实时回调最慢 |
| --- | --- | --- | --- | --- | --- | --- |
| 100,000 | 200,000 | 90.1 MB | 5,600 | 124.4 | 13.4 分钟 | 0.69 秒 |
| 300,000 | 600,000 | 263.7 MB | 4,630 | 102.8 | 48.6 分钟 | 1.31 秒 |
| 500,000 | 1,000,000 | 433.6 MB | 4,430 | 98.3 | 84.7 分钟 | 1.39 秒 |

三组实时请求均为 30/30 完成；只有三次注入波次，不能据此推断生产长期尾延迟。
大小使用十进制 MB，只包含本次人员相关表及其索引，不含 WAL、事件历史、备份和未来膨胀。

| 指标 | 10 万 | 30 万 | 50 万 |
| --- | --- | --- | --- |
| 运行中队列统计中位数 | 40.7 ms | 247.7 ms | 297.6 ms |
| 运行中队列统计 P95 | 86.4 ms | 351.8 ms | 359.9 ms |
| 测窗内统计调用累计耗时 | 3.22 s | 12.69 s | 14.63 s |
| 领取任务中位数（含少量实时小批次） | 26.9 ms | 28.4 ms | 28.4 ms |
| 单人完成事务中位数 | 1.37 ms | 1.35 ms | 1.38 ms |
| 热档案读取 P95，收尾后 1000 次微基准 | 1.50 μs | 1.50 μs | 1.60 μs |

采样结束前，三组均未记录 `refresh_errors` 或 `storage_errors`，`degraded=false`。
30 万组停止时出现一次批次失败日志，收尾后有 100 条任务进入重试；采样结束前无该错误。
这与 `close()` 设置停止事件后，已领取但尚未发出请求的批次走取消/失败路径一致，
不能当作正常运行时的 ESI 或数据库超时。另两组收尾失败任务为零。

收尾后数据库实际新鲜档案数分别为 5630、4630、4530。比测窗计数多的部分属于在途收尾，
没有纳入上表吞吐。三个测试 schema 均已删除，测试 PostgreSQL 已停止；原有数据目录未删除。

## 资源与可信度限制

本机不是独占压测环境。测试开始时可用内存约 972 MB；50 万组第 40 秒约 680 MB，
测窗末尾一次采样仅约 7 MB。停止并清理后可用内存回升约 2.56 GB。
因此不继续追加压力，不能把本次吞吐直接换算成 114 或 47 的服务器容量。

压测 Python 进程的测窗末尾 RSS 分别约 62、67、69 MB，包含测量开销和本轮几千条热点档案，
不包含 PostgreSQL 内存；三组在同一 Python 进程中顺序运行，不能把这些数字解释为独立进程
的全量常驻内存，更没有测到 2 万条热点缓存填满后的稳定占用。

## 已定位的开销与下一步

1. `PersonnelArchive.statistics()` 每次统计全量档案数及所有到期任务；
   `PersonnelRuntime._run()` 每个调度循环都调用它。50 万组测窗中统计累计消耗 14.63 秒，
   是明显的调度开销。建议将“有没有可领取任务”的调度判断与管理页面统计解耦，
   统计低频化，实时任务唤醒不能等待全量统计。
2. 虽然网络按 100 人批量，落库后仍逐人读取档案、完成事务、重读档案、查询军团和联盟。
   50 万组刷新 4430 人，调用 `get_profiles` 8860 次、`get_organizations` 10926 次
   （后者包含维护扫描），`finish` 4430 次。应优先批量读、批量组织名称装配，
   并在保留租约/版本防护的前提下改进批量完成事务。
3. 后台最大槽位为 4，不代表同类归属请求并发为 4；当前同一通道同一种任务最多一个批次。
   需要连同批大小、同类并发、实时资源预留和上游退避一起设计，不能只增大槽位数字。
4. 不能只将 100 改成 1000。当前 `upstream_batch_ms` 包含逐人 SQL 处理时间，
   又用于后台降速判断；只放大批次而不批量化落库、区分接口和本地耗时，可能造成反向降速。

以上为优化建议，本次未实施。改完后应在可控资源环境重复测试，并增加至少跨两个到期周期的
稳定性测试、慢上游/限流恢复、冷姓名解析，以及真实 SSE/机器人端到端时效测试。

## 复现

脚本：[benchmark_personnel_refresh.py](../scripts/benchmark_personnel_refresh.py)。
需 `psycopg`、`psycopg_pool`；可选 `psutil` 用于内存采样。
本次完整原始指标保存在本机 `.runtime/personnel-benchmark-20260911.json`，不纳入版本控制。

先准备专用本地测试 PostgreSQL（非 5432 端口），使用专用 `codex_test` 用户，
再设置 `EVE_SENTRY_TEST_POSTGRES_DSN`。脚本拒绝非回环地址、生产默认端口和其他用户名。
不要使用生产连接串或生产 SSH 隧道。

```powershell
python scripts/benchmark_personnel_refresh.py --rows 100000 300000 500000 --seconds 45 --latency 0.2 --confirm-local-test --output .runtime/personnel-benchmark-new.json
python -m pytest -q tests/test_personnel_benchmark.py
```

输出文件必须不存在。SQL 生成模拟数据，不把几十万人一次性加载为 Python 对象。
每组结束（包括异常）都会清理本组新建 schema；脚本不会自动停止用户自行启动的 PostgreSQL。
执行前应预留足够内存和磁盘，并避免与其他重负载任务并行。
