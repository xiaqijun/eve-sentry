# 系统架构

## 组件

| 组件 | 目录 | 职责 |
| --- | --- | --- |
| Windows 监控客户端 | `client/` | 窗口选择、截图、红框检测、OCR、身份日志校验、心跳和 SSE 预警浮窗 |
| 情报服务 | `app/server/` | 数据存储、角色解析、敌我分类、实时态、告警、认证和 SSE |
| Web 管理系统 | `frontend/` | 态势图、来袭报表、账号和管理员功能 |
| QQ 机器人 | `bot/`（独立进程部署） | 使用只读服务密钥读取 Bootstrap 和 SSE，发送主动预警 |
| ESI Gateway | `esi-gateway/`（独立进程部署） | 公共 ESI 代理、缓存、限流和健康检查 |
| 下载与更新服务 | `download-site/`、`deploy/cloudflare-download/` | 发布客户端/服务端公开文档，代理签名清单和版本化 Release 附件 |

生产服务端使用 PostgreSQL，启动时只加载有界热数据；JSON 存储仅保留为兼容模式。

人员资料实现见[全量人员档案与分级刷新](personnel-cache-plan.md)。启用 `on` 后，
PersonnelResolver 从有界内存读取，冷库加载和 ESI 批请求由独立调度器执行；PostgreSQL
分别保存身份、共享组织名称、租约任务和回填进度。实时 2 槽、后台最多 4 槽，不持实时状态锁请求 ESI。
当前名单来自有效观察，波次累计历史继续保留；刷新不能复活已清空人员。`off` 保留原解析链路，
`shadow` 仅写入/刷新档案，不切换消费者。
管理员人员配置保存在现有 `auth_settings` 中，保存与审计原子提交；启动读取已保存模式，
运行中通过 PersonnelController 在状态锁外准备资源、事务提交后原子发布解析器/增强器/运行时。
OCR 任务和资料读取固定使用进入时的依赖快照；模式版本变化后旧 OCR 结果不可写回，由工作线程
按新模式重试，已清空观察不复活。shadow/on 复用档案资源；off 恢复原解析器并异步收尾档案任务，
执行器完全结束后才关闭连接池。最多保留两个收尾中的资源组，达到上限时暂缓再次启用，不无限增池。
调度开关调整后续任务；全过程不重启服务、不主动中断 SSE，不修改视觉敌对人数。
已保存配置优先于环境默认值，API 分别返回预期配置与实际运行状态。

## OCR 与预警流程

```text
选中的 EVE 窗口
  -> 每轮只捕获一张成员列表区域截图
  ├─ 红色敌对图标检测（Presence，实时人数的权威来源）
  │    -> 立即更新本地预警
  │    -> POST /api/v1/hostile-presence
  │    -> 服务端更新 active intel、hostile wave 和状态事件
  └─ 名单区域变化或按需命令触发完整 OCR（增效信息）
       -> POST /api/v1/ocr/snapshot（只上传完整 OCR 文本名单，可带 query_id）
       -> 服务端逐名执行 ESI 解析和敌我分类
       -> 补充活动名单和人员详情
  -> SSE /api/v1/events
  -> Windows 预警客户端、Web 管理系统、QQ 机器人
```

Presence 和 OCR 共用同一轮截图，但承担不同职责。Presence 由红色敌对图标检测产生，是
敌对人数的唯一实时来源；即使关闭 OCR，Presence 仍继续运行并上报。OCR 只上传当前截图的
完整原始文本名单，用于身份解析、敌我分类和按需查询，不携带 `hostile_icon_count`，也不会
创建、续期、清除或覆盖 Presence。客户端方法中仍保留的 `hostile_icon_count`、
`ocr_candidates` 和 `hostile_icons` 参数仅兼容旧调用，发送前会被丢弃。客户端不自行查询
角色军团、联盟或 standings，也不上传坐标证据；视觉敌对人数与 ESI 已确认人员名单是两个
不同维度。
服务端维护实时名单的新增、刷新和消失状态，并且只把确认存在的角色纳入统计。
线上 PostgreSQL 另以星系聚合 active intel：0→>0 新建波次，>0→0 关闭波次。波次使用
独立追加式生命周期表，因此不会因 active-intel 的实体 ID 复用而覆盖上一轮记录，也不需要
在服务启动时加载全量历史。`hostile_waves.peak_hostile_count` 保存波次期间的视觉敌对峰值；
同一客户端的 Presence 与 OCR 行按 `client_id` 去重，同星系多客户端取当前最大红色图标数。
`hostile_waves.personnel_json` 同时累计波次期间已确认的敌对角色，因此即使告警快照不完整，
历史波次仍能显示已识别人员。OCR 没有识别出人员时，视觉波次仍然成立并进入历史统计。

红色敌对图标是即时预警的触发条件，会先触发本地星系预警并独立上传数量。OCR 在敌对图标
数量发生非零变化或名单区域画面变化时执行；完整 OCR 成功后立即结束当前重试，只有空结果
才有限补偿后续帧。客户端上传完整 OCR 文本列表，不在本地按敌我清洗，也不上传文字框或
图标坐标；OCR 后端内部产生的文字框仅供本地处理，序列化上传前会丢弃。服务端逐名
ESI 解析并分类。OCR 只补充角色、军团、联盟和敌我分类等有效
信息，不会阻塞、延迟或替代红色图标预警。多窗口共用一个有界 OCR
调度器，首轮扫描错峰执行，每个窗口的离线上传队列只保留最新数量，避免任务随扫描轮次
累积。服务端批量查询 ESI，持久缓存已确认身份、短时缓存未找到结果，并合并并发缓存缺失；
zKill 角色链接直接由 `character_id` 生成。服务端收到数量后立即更新事件流；星系敌对全部
消失时发布安全状态。

敌我分类在服务端完成，不能把截图中的共享红色图标计数直接附加到每一名 OCR 角色。对每个
角色，服务端优先使用明确的敌对证据（黑名单名称、敌对军团/联盟或敌对 standing）；只有在
没有敌对证据且 ESI 或白名单已确认友好时，才返回 `white` 并抑制该角色的共享红色图标证据。
身份尚未由 ESI 解析确认的 detector 角色不会进入敌对人员明细。敌对历史接口和活动告警构建
会排除 `white` 分类及 `friendly_*` 证据；读取旧的 detector `red` 快照时会重新核验持久化
身份资料，避免历史记录复活已确认的友军。这样“视觉敌对人数”与“已确认敌对人员数”保持
两个独立指标，机器人和 Web 页面都必须按接口提供的敌对名单消费，不能使用 OCR 原始名单
或单条告警的 `names` 长度自行推断。

## 当前星系与多窗口监控

客户端代码位于 `client/`，并定时发现 EVE 窗口。目标下拉框只决定当前校准和预览窗口，
“监控窗口”菜单可以同时选择多个窗口。开始监控后，每个已选且在线的窗口拥有独立采集
线程；运行中新增、取消或窗口下线时，只启动或停止对应线程，不需要整体重启监控。
窗口标题中的角色名用于匹配该角色最新的 Local 日志和当前星系，每个窗口保留自己的裁剪
区域；多个采集线程共享有界 OCR 调度器和上传管理器。

## 身份和权限流程

```text
EVE SSO、管理员密码登录，或管理员代签
  -> 创建桌面设备密钥
  -> 有效密钥立即获得客户端访问权限
  -> 密钥风控关闭：直接使用，不执行 ESI 身份任务
  -> 密钥风控开启且已配置 API Key：自动读取最近修改的 EVE 日志
  -> 从文件名末尾取得 character_id 后 POST /api/v1/client/identity-checks
  -> PostgreSQL 幂等任务立即确认
  -> 服务端 worker 异步解析并退避重试
  -> 允许军团或用户角色白名单持续风控
```

客户端在开启功能前只校验密钥是否可用。配置 API Key 后，Listener 身份扫描会自动运行，
无需额外开关；它仅检查最近 24 小时修改过的 `Local` / `本地` 日志，按文件名末尾的
`character_id` 分组并只读取每个角色最新的一份，最多处理 64 个角色。
后续仅在目录变化或每 30 秒兜底检查时发现新增文件；API Key 变化保留已处理文件记录，不回放历史。
认证或网络失败按 30 秒到 10 分钟指数退避。没有 Listener 不算
失败，发现新角色 ID 时才提交校验。客户端重复提交同一 ID 集合只读取既有任务状态，不会
重复调用 ESI 或记录成功日志；服务端直接按 ID 查询角色和军团资料，不执行名称搜索。确认
违规会禁用整个用户并吊销全部会话和密钥。

## 预警客户端、SSE 与局部星图

`GET /api/v1/events` 是有界长连接：服务端默认在 30 秒后正常结束本次响应，并默认每
15 秒写入 SSE 注释心跳。Windows 客户端和 QQ 机器人都请求 1 秒注释心跳，并把连续 15 秒
无字节作为失活连接的重连边界；正常流结束后立即重新连接，只有请求错误才进入有上限的
指数退避。

SSE wire 事件名是 `bootstrap`、`alert`、`safe` 和 `monitoring_node`。持久化状态事件在
`data.event_type` 中使用 `alert.entered`、`alert.updated` 和 `alert.cleared`；其中前两者
映射到 wire `alert`，后者映射到 wire `safe`。持久化状态事件使用 `state:<sequence>` 作为
事件 ID。客户端把已确认的最高状态序号保存到用户目录的 `alert_client_state.json`，并在
重连时通过 `Last-Event-ID` 恢复；后续 `presence_*`、报告或节点 ID 不得覆盖该可靠游标。
PostgreSQL 流在派生告警后用无 `data` 的 `id: state:W` 控制块恢复原生 EventSource 游标；
该块只改变浏览器重连位置，不进入应用事件处理。

PostgreSQL 用一条一致性查询读取 active 条目、其引用报告和状态事件水位 `W`。SSE 先按页
追平 `seq <= W` 的持久事件，再发送 `state:W` Bootstrap；所有状态写事务在分配事件序号前
取得同一事务级 advisory lock，保证已提交序号形成前缀。这样内存先更新、数据库后提交或
跨进程并发写入都不会产生 `safe` 后跟旧 Bootstrap、或高序号游标跳过晚提交低序号的问题。
快照告警只使用该查询返回的报告及其中的身份元数据，不读取进程/磁盘实时缓存；OCR/ESI
丰富产生的报告、active 条目、波次和状态事件也按锁内冻结的状态快照与 FIFO 票据，在释放
内存锁后用同一事务提交，避免旧水位看到未来身份或较早写入反向覆盖较新状态。

`bootstrap` 在首次连接以及服务端状态指纹变化时发送；监控节点发生变化时，服务端先发送
`monitoring_node`，随后发送权威的 `bootstrap` 快照。客户端没有固定的 30 秒 Bootstrap
轮询。`monitoring_node` 主要用于提示变化，实际节点集合和状态以伴随的 `bootstrap` 为准。
全新客户端没有游标时直接以当前快照水位初始化，不回放 14 天保留历史；显式 `state:0`
才表示从保留日志起点重放。

Windows 客户端只为选中账户请求局部拓扑，不下载整张星图。拓扑请求在后台
`AlertMapWorker` 线程中执行，请求超时为 5 秒；已有请求运行时只保留最后一个待处理请求，
因此不会阻塞覆盖层界面。可见节点健康状态为 `online`、`degraded` 或 `offline`：青绿色
表示在线，黄色表示降级，灰色表示离线；`removed` 是移除变化，节点不会继续出现在可见
集合中。节点健康状态本身也是账户渲染签名的一部分，所以即使星系和敌对人数不变，健康
状态变化也会立即刷新星图。默认 10 秒 detector 心跳带半个周期、最多 5 秒调度宽限，节点
约在 15/25/35 秒依次进入 `degraded`、`offline`、`removed`，避免 1～3 秒上传抖动造成
全部子窗口反复黄绿切换。

## Web 与部署边界

Python 服务只提供 JSON API 和 SSE，不托管旧内嵌网页。生产环境由 OpenResty/Nginx
托管 `frontend/dist`，并把 `/api/` 反向代理到 `127.0.0.1:8765`。SSE 路径必须关闭
代理缓冲。

PostgreSQL 连接由 `psycopg_pool` 复用，默认最小 2、最大 8 个连接。SSE 每 30 秒重新
检查一次认证状态，用户或密钥状态变化时会主动唤醒连接检查。

历史报告和观察记录通过 PostgreSQL 键集分页读取，普通列表默认最多 100 条。角色和星系
详情在 SQL 中按实体过滤；写入响应按 observation ID 点查对应告警。告警历史按时间倒序
惰性生成，达到请求上限后停止评分。预警 SSE 不读取完整 Bootstrap，也不扫描全部历史；
首次精简快照同时包含当前红色图标 Presence 和活跃情报引用的报告。

客户端从本地聊天日志确认星系变化时，会立即清除旧星系的本地预警，并强制下一帧把当前红色
图标数量重新上报到新星系；即使前后数量相同，也不会把旧星系的红色状态遗留在星图上。

公共 ESI 的角色、军团、联盟和星系资料可经 `esi-gateway/` 独立进程访问；Gateway 只处理无令牌的
公共接口，服务端保留本地回退。认证 ESI（SSO、contacts、standings、location）及其
按授权账号隔离的声望快照仍由服务端直接请求，默认 TTL 为 600 秒。缓存和部署参数以
[服务端部署](server-deployment.md#公共-esi-gateway) 和 [Gateway 运维文档](../esi-gateway/docs/operations.md) 为准。

机器人执行指定星系、人员、军团、联盟或所有节点名单查询时，会创建一次性 OCR 任务，
服务端通过 detector heartbeat 下发给目标客户端，客户端上传带 `query_id` 的快照后再由
服务端聚合返回；“查询节点敌情”和“查询预警节点”只读取现有状态，不创建 OCR 任务。协议细节见
[按需 OCR 对接说明](../client/docs/on-demand-ocr-query.md)。
命令在目标客户端回传结果前可随后续心跳重复下发；客户端应按 `query_id` 去重。这样即使
心跳响应丢失、窗口线程正在重启或客户端短暂重连，也不会把一次性查询永久丢弃。

## 数据来源

- Presence：当前截图中的红色敌对图标数量，是实时敌对人数、活动预警和 hostile wave 的权威来源。
- OCR：当前 EVE 成员列表的完整文本名单，用于 ESI 身份解析、敌我分类和按需查询；不包含敌对人数，也不改变 Presence。
- EVE Chatlogs：客户端身份 `Listener`、所选角色当前星系；独立频道采集仍为兼容功能。
- ESI：角色、军团、联盟、standings、EVE SSO 和可选态势页授权。
- SDE：星系和星门拓扑。
- zKillboard：已解析角色的威胁度、击毁和损失等历史统计；在异步身份补全阶段按角色限速
  查询并缓存，只用于工作台和来袭分析研判。

zKillboard 不参与敌我分类和告警生成。外部服务失败时保留 ESI 分类结果，页面将缺失统计
显示为暂无数据，不构造战报数量或其他不存在的数据。
