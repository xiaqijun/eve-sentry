# QQ 查询与上线监测实施方案

本文冻结 QQ 机器人查询菜单、按需 OCR 和上线监测的产品语义。实现不得把实时
Presence、历史预警数据和一次性 OCR 名单混为一套状态。

## 1. 查询菜单

`@机器人 查询` 只打开 Markdown 查询菜单，不直接发起 OCR。优先使用
`QQ_QUERY_KEYBOARD_ID` 指定的 QQ 静态按钮模板；未配置模板时发送相同布局的内联键盘。
QQ 拒绝两种键盘时才退化为普通 Markdown。固定动作使用回调按钮，需输入名称的动作使用
指令填充按钮：

| 按钮 | 指令数据 | 类型 | 点击行为 |
| --- | --- | --- | --- |
| 查询指定星系 | `查询星系 ` | `type=2` | 填入输入框，补名称后发送 |
| 查询节点敌情 | `查询节点敌情` | `type=1` | 回调并直接执行 |
| 查询指定人员 | `查询人员 ` | `type=2` | 填入输入框，补名称后发送 |
| 查询指定军团 | `查询军团 ` | `type=2` | 填入输入框，补名称后发送 |
| 查询所有节点 | `查询所有节点` | `type=1` | 回调并直接执行 |
| 查询指定联盟 | `查询联盟 ` | `type=2` | 填入输入框，补名称后发送 |
| 查询预警节点 | `查询预警节点` | `type=1` | 回调并直接执行 |
| 上线监测 | `上线监测 人员 ` | `type=2` | 填入输入框，补目标和间隔后发送 |

机器人必须开启 `interaction` intent。收到 `INTERACTION_CREATE` 后先在 3 秒内调用
`PUT /interactions/{interaction_id}` 确认，再按 interaction ID 去重并执行固定回调动作。
群聊不能依赖 `type=2` 的 `enter=true` 自动发送；文字指令始终作为最终降级路径。

## 2. 数据语义

| 功能 | 是否触发 OCR | 权威数据 |
| --- | --- | --- |
| 查询指定星系 | 是，只查询该星系符合服务端选择条件的监控目标 | 本次 `query_id` 的原始名单 |
| 查询节点敌情 | 否 | 服务端当前活动预警数据 |
| 查询指定人员 | 是，查询全部符合条件的监控目标 | 本次 OCR 名单及服务端识别结果 |
| 查询指定军团 | 是，查询全部符合条件的监控目标 | 本次 OCR 与 affiliation 结果 |
| 查询所有节点 | 是，查询全部符合条件的监控目标 | 各目标本次完整 OCR 名单 |
| 查询指定联盟 | 是，查询全部符合条件的监控目标 | 本次 OCR 与 affiliation 结果 |
| 查询预警节点 | 否 | heartbeat 与 `monitoring_nodes` 状态 |
| 上线监测 | 按调度需要 | 最新成功的完整 OCR 名单 |

这里的“符合条件”按现行服务端实现指父 detector heartbeat 在线且目标 `monitoring=true`。
单目标 `capture_online=false` 当前不会被目标选择器排除，因此仍可能计入预期响应数但无法
返回 OCR；结果必须区分 `received_clients` 与 `expected_clients`。

### 2.1 查询指定星系

指令为 `查询星系 S-KSWL`。服务端只向当前 heartbeat 中 `system_name=S-KSWL` 且符合上述
条件的监控目标下发命令。结果只返回去重后的人员名称和响应节点数，不返回敌我、军团、联盟、声望、
星系资料或 zKill。历史活动名单不得补入本次结果。

### 2.2 查询节点敌情

指令为 `查询节点敌情`。直接读取 `/api/v1/bootstrap` 中的当前活动预警数据，按星系输出
敌对人数和已识别人员，不创建 `query_id`，也不唤醒客户端 OCR。

### 2.3 查询人员、军团和联盟

指令分别为 `查询人员 <名称>`、`查询军团 <名称>` 和 `查询联盟 <名称>`。服务端向全部
符合条件的监控目标下发一次 OCR，机器人只筛选本次返回的名单。军团和联盟使用角色 affiliation
结果判断，不允许用历史预警名单补齐。

### 2.4 查询所有节点

指令为 `查询所有节点`。向全部符合条件的监控目标下发一次 OCR，按节点和星系返回本次完整
人员名单，包括没有被判断为敌对的名称。空数组表示窗口本次确实没有识别到人员。

### 2.5 查询预警节点

指令为 `查询预警节点`。读取 `/api/v1/bootstrap` 中由服务端统一规范化的
`monitoring_nodes`，用 Markdown 表格返回节点、状态、星系和当前敌对人数，不触发 OCR。
完整 Bootstrap 与 SSE 精简 Bootstrap 必须共用同一套节点生成逻辑，避免查询结果与实时
节点推送不一致。该功能用于查看基础设施健康，不能用它替代“查询节点敌情”。

## 3. 异步查询响应

主动 OCR 查询必须拆分为创建和等待两个阶段：

```text
用户指令
  -> POST /api/v1/ocr/query
  -> 立即回复目标节点数和“任务已下发”（query_id 仅内部使用）
  -> 客户端在下一次 detector heartbeat 响应中领取命令
  -> 机器人后台轮询 GET /api/v1/ocr/query/{query_id}
  -> 全部返回或达到软超时
  -> 主动发送 Markdown 结果
```

同一群同时只允许一个主动 OCR 查询。Redis 锁和 `query_id` 投递标记防止按钮连点、事件
重放或后台任务重复发送。查询菜单、节点敌情和预警节点不占用 OCR 查询锁。

## 4. 上线监测

“上线”定义为目标出现在监控客户端当前人员名单中，不表示 EVE 账号登录状态。人员使用
大小写无关的完整名称匹配；军团和联盟使用大小写无关的完整名称或 ticker 精确匹配，不做
模糊包含。支持：

```text
上线监测 人员 Alice 30s
上线监测 军团 Rat Nation 1m
上线监测 联盟 Example Alliance 5m
上线监测列表
取消上线监测 M001
取消上线监测 人员 Alice
取消上线监测 军团 Rat Nation
取消上线监测 联盟 Example Alliance
取消全部上线监测
```

- 最低间隔为 30 秒，默认 60 秒；
- 监测任务持久化到 PostgreSQL；
- 同一调度轮次的到期规则合并执行，并使用 Redis 锁避免多个实例并发创建全节点 OCR；
- 只有 `expected_clients > 0` 且 `received_clients >= expected_clients` 的成功完整快照会被缓存，
  默认 30 秒内优先复用，不重复唤醒客户端；
- 失败、零目标或部分返回不会进入复用缓存，下一次默认 5 秒调度轮询可以重新尝试；
- `未出现 -> 出现` 只通知一次；
- 连续两次成功完整 OCR 未发现后重新布防；
- 节点离线、OCR 失败或部分节点未返回不能作为目标消失依据；
- 删除 PostgreSQL 记录后不再调度；当前没有每条监测规则独立的 Redis 运行态需要清理；
- 单条删除支持任务编号或“类型 + 名称”，批量删除使用独立明确指令。

## 5. 现行时序与性能目标

- 查询菜单、节点敌情和预警节点的体验目标是正常情况下 1 秒内返回；
- detector heartbeat 默认为 10 秒、最短 5 秒，主动 OCR 命令最多先等待下一次 heartbeat
  领取；机器人随后每 0.5 秒轮询查询状态；
- 机器人 15 秒软超时时，如果已有部分结果就返回并显示响应节点数；完全没有结果则报告
  超时。服务端查询任务默认最多保留 30 秒；
- 指定星系 OCR 的体验目标是 5～10 秒，全节点 OCR 是 7～15 秒；实际时延还包括等待下一次
  heartbeat 的时间；
- 同一 `run_once` 最多合并 200 条到期规则并共用一次全节点 OCR。之后 30 秒内的复用仅限
  同一机器人进程中的成功完整快照，不是跨实例的分布式缓存；
- 查询 OCR 不能修改 Presence、波次、地图红色状态或正常预警清空逻辑。

## 6. 实施与验收

1. 机器人支持静态查询按钮模板和无模板降级；
2. 服务端 `/api/v1/ocr/query` 支持可选 `system_name` 精确选择目标窗口；
3. 查询客户端拆分创建、等待和结果格式化；
4. PostgreSQL 增加上线监测任务表，机器人启动监测调度器；
5. 覆盖按钮 payload、命令解析、星系目标筛选、无 OCR 快速查询、查询锁、监测间隔、
   状态去重和删除操作测试；
6. Pull Request 先通过独立的 `Contract Compatibility`；合并后，只有命中服务端或机器人
   代码路径的变更才分别触发各自验证与生产部署。契约 workflow 不是两个部署 workflow 的
   `needs` 门禁，纯文档变更不会部署服务。
