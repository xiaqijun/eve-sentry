### 本地开发进度与未完成项

首批代码实现（未提交、未部署）：

- 私有联系人读取全部页后才返回，严格校验 ID、类型、声望、重复记录及页数；异常不会变成空关系表。
  完整成功空表仍撤销该来源关系。己方角色资料读取失败也不会伪装成“没有军团/联盟”。
- 联系人专用 HTTP 读取保留缓存元数据；按剩余有效期刷新，支持同令牌上下文内 ETag/304，
  无对应成功体的 304、失效响应或缺失有效期的真实 HTTP 响应不能续期业务快照。
  不改公共 ESI 查询 envelope，也没有把私有令牌发送到 Gateway。
- 每页最多 4 MiB、整个来源最多 8 MiB/20,000 条/100 页；分页和分块读取采用 30 秒软预算，
  每次网络调用另受原 socket timeout 限制。不是 DNS/底层系统调用可强制取消的严格墙钟保证。
  条件请求缓存最多保留 6 个令牌摘要/来源组合，仅存内存，不落盘，不记录令牌。
- `on` 的后台联系人刷新和 `off/shadow` 原增强器共用失败保护：同授权、同己方组织上下文的成功关系
  最长降级使用至成功时间后 1 小时，失败不续期；401/403 立即隔离。已确认换组织后读取失败也不复用旧组织关系。
  授权主体在请求期间切换时拒绝旧结果；同一增强器只允许一个联系人刷新任务。
- 网络失败从约 30 秒指数退避至约 300 秒并增加 0～10% 抖动；401/403/420/429 至少等待 300 秒，
  更长的 Retry-After 优先。成功截止时间已逼近时最短重查间隔 5 秒，避免热循环。
- 新增脱敏联系人读取/失败日志以及 `EsiClient.contact_metrics()` 进程内计数。
  `requests/success/errors` 是逻辑完整来源请求；`attempts` 是实际分页请求，`not_modified` 是收到的 304 数，
  可能属于最终失败的分页批次。不等于客户端端到端失败率；尚未新增管理界面指标。

第二批组织关系阶段（本地实现，未部署）：

- C 节两项规则均已确认并实现：不保留个人例外；同一目标己方军团来源优先，目标军团先于目标联盟。
  `on` 模式的人员增强器使用 `OrganizationRelations`，不请求个人联系人或角色 standings；
  既有通用 ESI 快照接口与 `off/shadow` 原增强器保留兼容行为，不能把此变更称为全局删除个人接口。
- 增量表 `personnel_relation_snapshots` 按授权/己方组织上下文、来源类型及 ID 保存成功时间、期限、
  失败/授权状态和版本；`personnel_relation_entries` 仅保存军团/联盟目标的正、负、零关系。
  数据只进 114 PostgreSQL；初始化依附现有人员档案资源准备，不改变默认 mode，不自动改生产库。
- 军团与联盟分开刷新、分开原子提交。单个来源异常不阻止另一个来源更新；缺失高优先级来源不跳过。
  表替换与版本同事务；版本比较防止旧写者覆盖新结果。关系行每批最多 100 条插入，不逐条提交事务。
- 不可变 `RelationView` 按源版本组合复用，人员匹配只查预建字典；缓存硬过期时产生新视图，
  现有 OCR contacts guard 可拒绝使用旧视图完成的任务。热读无 DB/ESI/令牌文件访问。
- 身份/权限变化先隔离，己方组织每约 300 秒重查；完整上下文包含己方军团和联盟 ID。
  启动恢复不重置关系成功时间或 Retry-After。暂时失败可用同上下文旧关系，但不得超过成功后 1 小时。
  401/403 运行中立即禁用来源，即使状态落库失败也不继续用它确认友军。
- 原始声望数值不改写；`standing_source=esi_organization` 时按正数友好、零/负数敌对判定，
  独立黑白名单仍保留现行优先级。未知关系使用 `esi_organization_pending`，清除旧声望字段，
  服务端、前端与 QQ 均避免从旧扁平元数据重新继承个人声望；视觉 Presence 来敌/清空独立运行。

第三批基础能力（2026-09-13，本地实现，未部署）：

- 同一令牌文件的 SSO 刷新串行合并，刷新结果按令牌和本地修订号比较保存；登录/退出优先于
  旧刷新结果。令牌使用同目录临时文件、fsync 和原子替换；仅保证当前单服务进程，非跨进程分布式锁。
- 组织关系恢复后先隔离，再进行权限校验；成功前不用于确认友军，避免撤销权限落库失败后重启恢复旧授权。
- 一批人员结果共用事务，提交成功后才更新热缓存；批量加载资料/组织、提级任务和出现时间。
  调度循环改为索引存在性查询，全量统计每 30 秒更新一次；组织名称已有记录按 90 天低优先级校验。
- `affiliation_expires_at` 增量字段持久保存官方剩余期限；归属可信性同时受该期限和获取后 1 小时上限约束。
  旧记录没有新字段时保持原期限，不伪造重新获取。新转发路线读取响应头，缺少可靠期限时立即标为过期。
- 人员档案 `mode` 与 `organization_mode` 分开：组织模式默认 off（旧规则），shadow 只比较声望符号，
  on 才应用纯组织分类；组织模式需要档案 mode=on 才执行。旧管理客户端省略新字段时保留已保存值。
  两种模式在线切换，不重启或中断 SSE。比较次数按调用计数，不是去重人数或完整旧分类器误差率。
- Gateway 新增 legacy/dual/relay 三种传输模式，默认 legacy；dual 保留旧 JSON 路由并接受固定目标 CONNECT，
  relay 关闭旧 JSON 缓存路由和 ID 缓存后台队列。只接受显式内网绑定、来源白名单和 Gateway 凭据；
  目标固定为 `esi.evetech.net:443`，最多 8 个隧道、16 个请求线程，30 秒空闲/300 秒连接寿命和 64 MiB 流量上限。
- 114 显式 `EVE_SENTRY_ESI_TRANSPORT=relay` 使用端到端验证的 TLS、6 个共享连接和默认 2 请求/秒预算；
  Gateway 凭据只用于 CONNECT，ESI 私有令牌只出现在端到端 TLS 内。420/429 进入共享退避，
  不重试或切换出口；direct 为显式直连应急模式，legacy 保持原配置路线。网络时限仍受底层 DNS 行为约束。
- 预警启动只在当前启用周期续接 SSE 游标，避免先重放上次磁盘游标造成闪动；相同内容不重复调整浮层布局。

### A. 114 与 47 的职责

| 组件 | 目标职责 | 不承担的职责 |
| --- | --- | --- |
| 114 服务端 | 长期人员档案、共享组织资料、私有关系快照、刷新队列、敌我分类、星系当前状态和事件 | 不因实时来敌等待外部 API；不扫描全游戏人员或组织 |
| 47 Gateway | 优先承担 ESI 请求转发；连接复用、有限并发、超时、限流信号透传和请求指标 | 不保存人员/组织成功缓存或私有关系表；不运行档案刷新队列或计算敌我 |
| 监控客户端 | 采集 Presence、OCR、采集健康和来源版本 | 不合并其他节点状态，不将人员解析失败当清空 |
| 星图、预警端、QQ | 消费 114 发布的同一星系状态和版本化事件 | 不各自再次访问 ESI 判定敌我 |

已有 Gateway 缓存不能先删再迁移：先验证 114 的缓存、批量读写和请求去重，再按功能开关切换。
47 的“只转发”仍包括必要的安全与资源保护，不等于无限制转发或没有超时。

公共查询优先走 47；联系人私有查询也以经 47 转发为目标，但需要单独实现和验收安全传输。
当前生产私有联系人仍由 114 直连 ESI；测速中的临时 TCP 通道不是已发布的 Gateway 功能。
建议使用固定目标的 TLS 透传，使 ESI 登录令牌、刷新令牌只由 114 管理，114 验证官方证书和主机名，
47 不解密、不记录联系人请求内容。转发通道须限制来源身份、目标 `esi.evetech.net:443` 和连接数，
采用受认证的内网传输/访问控制，不开放通用公网代理；不得关闭 TLS 校验。
不复用公共 JSON envelope 来携带私有令牌，SSO 授权/刷新流程不随测速自动迁移。

直连仅作为显式受控的应急路线，不按单次耗时反复切换；420/429 不得通过切换出口规避限流。
需要分别记录首个尝试、回退尝试和最终结果，防止重试掩盖错误率；正式超时预算须覆盖转发开销，
避免 114 的等待期限先于 47 的上游期限耗尽。所有外部等待均在后台，不持有星系状态锁。

### B. 人员与组织资料：长期保存、按活跃度刷新

- 全量档案只包含实际遇到且经 ESI 确认身份的角色；不建立全游戏军团/联盟全集。
- 人员 ID 是身份主键，军团和联盟按正整数 ID 比较；名称缺失不能阻塞分类，zKill 链接由人员 ID 生成。
- 姓名和组织名称长期保存。姓名定期低频核验、改名时维护旧索引；组织名称新 ID 按需补齐，
  已有名称低优先级校验，不能因名称陈旧阻塞告警。不恢复战绩、威胁评分或等级请求。
- 当前人员归属过期/缺失优先刷新；24 小时内出现人员次之，1～7 天人员利用剩余容量；更久历史
  仅在有余量时刷新，再次出现立即提级。不再承诺几十万历史档案每小时全部刷新完成。
- 归属有效期维持官方当前约 1 小时的边界；人员分级只影响排期，不能把过期值改成新鲜值。
  有可靠响应头时按官方剩余有效期计算，不简单以“本地读到的时间 + 1 小时”延长官方期限。
- 过期档案可以先展示身份和上次归属，分类标记待确认；过期友军资料不能作为屏蔽来敌的唯一证据。
  不把待确认直接算成已确认敌对，不因资料过期删除身份或伪造人员离场。
- 真正未找到的姓名可短期负缓存；超时、授权失败、限流和服务端错误不能变成 not_found。

刷新队列持续运行并去重；历史任务在再次出现时可提级，但不取消合法的失败退避或在途租约。
降低全量统计频率、按索引分页领取、批量读写档案和组织资料；禁止每个调度周期全表统计和逐人多事务。
实时任务须保留执行、数据库连接及上游请求预算，冷任务不能占满这些资源。空闲判断同时考虑
实时积压、数据库等待、上游延迟和限流，不仅看 CPU。后台逾期年龄可观测，但不是无限抢占实时容量的理由。

### C. 私有声望关系表与判定规则

维护“己方授权组织 → 目标”的有向关系，不把声望作为某军团或人员的全局属性。
建议新增的逻辑模型（名称和 wire 字段均未定版、尚未迁移）：

| 数据 | 关键字段/约束 |
| --- | --- |
| 关系快照元数据 | 授权上下文、来源类型/ID、版本、成功验证时间、expires_at、页数、完整性、错误/退避状态 |
| 关系明细 | 快照版本 + 目标类型 + 目标 ID；保留官方 standing 值及来源，不靠姓名匹配 |
| 内存分类索引 | 由完整快照一次构建、原子切换；不得为每个人重新构造整张联系人字典 |

组织目标明确设置的正、负、**零**关系均保留；未设置的目标不建记录，查询默认 0。
例如目标军团显式 0、目标联盟 +5 时，军团 0 必须能阻止继续继承联盟 +5。
只有快照成功、完整且适用于当前授权上下文时，“未命中”才能解释为默认 0；
缺失权限、尚未加载、分页不全或失效快照均不能解释为全体中立。

纯组织级分类的建议顺序：

1. 新鲜且有效的同军团 ID，或双方均有有效的相同联盟 ID → 友军。两个空联盟 ID 不相等。
2. 查目标军团的显式关系；没有才查目标联盟关系。
3. 完整可用快照内都未命中 → 0；大于 0 为友军，小于或等于 0 按用户规则视为敌对。
4. 必要资料未知时保持待确认，不用猜测、旧姓名或共享图标给每个人强行分类。

分类决策（2026-09-12 更新）：

- **来源冲突（用户已确认）**：同一目标由己方军团、己方联盟设置了不同值，己方军团设置优先；
  先按目标类型（军团 → 联盟），同一目标再按来源（己方军团 → 己方联盟）查找。
  显式 0 也会终止查找；高优先级来源不可用时不能跳过它使用低优先级结果。
  此为本系统已确认规则，不声称已验证与游戏显示完全一致。
- **个人例外（用户已确认不保留）**：组织级分类不使用个人联系人来源，也不使用军团/联盟
  联系人中目标类型为 `character` 的正、负或零声望。仅组织关系及同组织规则参与判定；
  个人正声望不能豁免敌对组织，个人负声望也不能覆盖友好组织或同组织规则。
  9 月 12 日实测，军团表含 21 条、联盟表含 283 条个人目标关系，共 304 条记录（未跨来源去重）。
  这些记录不进入生效的组织关系表/分类索引；仍须完整读取并校验接口分页，不能把过滤结果为空
  与读取失败混淆。此决定不删除人员身份、军团/联盟归属档案或既有历史原始记录。
  不影响独立白名单机制；如需调整白名单，另行明确范围。以上为已确认目标规则，尚未上线。

### D. 联系人刷新与失败保护

官方当前三个联系人接口均采用约 300 秒缓存，并支持 `page`；按各来源返回的 `Expires`、`Date`、
`Age`/`Cache-Control` 等可用信息计算剩余有效期，遵循 HTTP 缓存语义，不忽略响应已消耗的年龄。
响应头缺失/矛盾时标记退化并采用明确的保守期限，不伪造刚刚验证成功；支持条件请求，304 只有在
存在对应成功缓存体时才能复用，并按新响应元数据更新验证期限。
参考：[官方 OpenAPI](https://esi.evetech.net/meta/openapi.json)、
[官方分页说明](https://developers.eveonline.com/blog/changing-pagination-turning-a-new-page)。

- 按授权来源刷新整张关系表，不逐人请求。通过 `X-Pages` 获取所有页，设置总时限和有限分页并发。
- 各页先写暂存版本，校验结构、目标 ID、重复冲突和分页完整性，再原子替换该来源快照；
  拉取失败不清空旧表。跨页变化/页数变化时放弃不完整版本并退避重读，不声称 ESI 提供跨页事务快照。
- 成功获取完整空表才表示关系全部撤销；单页失败、异常返回空列表、己方归属查询失败都不是空表。
- 军团和联盟分别保存成功状态；某一来源失败不得把另一来源标记失败，也不得把失败来源当作不存在
  来改变覆盖规则。分类使用带版本的完整快照组合；不确定的高优先级来源不能静默跳过。
- 失败保留同上下文的成功数据并显示 stale/degraded；建议降级使用的硬上限为距最后成功验证 1 小时，
  超限则不可用于确认友军。401/403 等授权异常立即隔离为不可用，提示授权检查，不按普通网络错误无限重试。
- 429/420 尊重 Retry-After；网络/5xx 指数退避加抖动。重试不延长资料有效期、不改变成功时间。
- 己方角色换军团、换联盟、授权主体或权限变化时切换上下文并失效旧分类结果；上下文包含己方组织 ID，
  不能仅由角色 ID、owner hash、scopes 判定“没有变化”。刷新令牌由 114 单点协调，避免并发刷新覆盖。
- 移除失败吞成空列表的分支，同时记录接口类别、HTTP 状态/异常类别、阶段耗时、页号和重试原因；
  不记录令牌、Authorization 头或完整私有联系人响应。

### E. 每个星系一个主监控来源

主来源粒度为“客户端监控实例/窗口 + 本次监控会话”，不是整台客户端。一个共享星系状态表按
规范化星系键一行保存当前结果（兼容原事件键，`system_id` 保留在载荷），不为每个星系创建一张表；原始 OCR 上报、明细和历史事件继续保留。
状态至少包含主来源、主来源任期、最新采集序号、视觉人数、当前确认名单/待确认状态、状态版本和健康度。

- 服务端按首次有效进入该星系的顺序分配入队序号，连续驻留最久的合格来源优先；不用客户端时钟排序。
- 主来源健康时不因备用节点更快而抢占。后来上线者备用，其最新候选结果有界保存，不混入当前名单或人数。
- 主来源多次独立采集可信地显示名单截断，且存在合格备用来源时，原子提升最早的合格备用者。
  恢复的旧主来源回到队尾，不能用历史上线时间抢回主位；正常停止/离开星系后重新加入也排队尾。
- 截断不是“姓名未解析成功”；重传同一帧不能算多次异常。建议初始门槛为最近 5 次独立采集中 3 次明确截断，
  该阈值仍需回放验证，不是现行生产参数。不通过模糊匹配自动绑定两个真实存在的相似角色名。
- 心跳存活不代表采集可用；监控新的成功采集序号、有效采集区域和数据新鲜度。画面不变但持续成功采集正常。
  失联门槛必须覆盖实际扫描/上报周期，不直接套用“3 秒无更新就接管”造成抖动。
- 接管要同时切换人数、名单、任期和版本。旧主来源、旧监控会话及旧 OCR/ESI 异步结果不能覆盖新主来源。
- 主来源有效清空不等待备用来源清空或外部解析；没有合格备用时显示降级。名单不可靠但视觉人数有效时保留人数；
  整个采集失效时保留“上次状态/未知”，不能假装当前为零。
- 单主方案解决混源，不保证主来源 OCR 永远正确。采集质量字段缺失的旧客户端须明确降级策略，不能直接宣称可靠。
- 手动/频道上报、QQ 按需查询仍保留原用途，不参与自动监控主来源竞争；是否与监控告警并存须在 API 兼容设计中明确。

### F. 当前状态、推送与可靠性

114 只对当前主来源结果计算星系状态；状态更新和持久事件同一事务提交，再唤醒 SSE。
星图、预警端和 QQ 消费相同版本，Bootstrap/游标对账用于初始化、断线恢复和漏事件修复，
不充当实时计算或清空触发器。当前客户端规模不要求为本方案改用 WebSocket。

异步结果应用时同时校验监控会话、主来源任期、采集序号、人员归属版本、关系快照和规则版本。
人员已离场/星系已清空时只更新长期档案，不重新推送旧敌对名单。当前名单与历史累计名单分离。
名称变化、资料内容未变或组织变化但敌我分类不变，不重复预警；敌我分类确有变化才更新当前名单并推送。
人员消息标题继续采用“敌对事件”，不恢复“人员名单更正”标题。
QQ 按星系顺序和事件版本去重，投递前校验名单消息是否已过时；不得因全局跳过旧版本而丢失真实来敌/清空事件。
离线/未知不是确认清空，节点在线变化与敌情变化独立，来敌不能顺带触发节点列表通知。

### H. 开发顺序、验收与回滚

1. 先补指标及失败保护：错误不当空表、分页完整性、上下文隔离、按官方到期时间刷新。
2. 落实 C 节已确认的“不保留个人例外、己方军团来源优先”；落地 114 关系快照、组织索引、分级调度和批量数据库访问。
3. 实现受控转发及连接复用；同窗口、同接口比较两条路线，验证 114 缓存接管后再关闭 47 成功缓存。
4. 实现单主来源、星系当前状态和旧结果隔离，联调星图、预警端、QQ 和 Bootstrap/事件游标。
5. 按受保护 GitHub 工作流灰度发布；影子计算不能产生第二套告警。验收后统一 API、设计、客户端指南和发布台账。

档案、组织规则和网络路线分别控制；单主来源/当前状态读写作为同一服务端版本发布，不能拆开开启写侧或读侧。
数据库增量迁移不删旧档案，保留兼容读取及回滚窗口；回滚不重放已完成告警、不恢复已失效的旧主节点。
本节的表名、状态字段、主来源健康参数仅为设计要求；实施前必须对照
[monorepo 开发流程](monorepo-development.md)及 [API 参考](api-reference.md)完成 wire/消费者兼容设计，
未实现内容不得提前写入当前 API 能力或生产操作说明。

验收至少包括：单页/多页/空表/中途失败/304/429/401/403；来源冲突/显式零/个人正负零关系均不参与分类/同组织空 ID；
授权与己方组织变化；双节点错峰清空、快速开关、反复截断、旧节点迟到、旧解析结果回写；
后台大积压下实时延迟；网关失联、ZeroTier 重启、服务重启后恢复；QQ 积压、SSE 重连和无重复投递。
统一观测逻辑请求数、实际尝试数、首尝试失败、最终失败、回退、各阶段耗时、P50/P95/最大值，
按路由和时间窗口分组。SSE 首字节/事件滞后、采集到 114、114 到消费者、QQ 队列/实际投递分别计时，
不能把数据库查询耗时或官方请求耗时当完整预警延迟。

以下为此前设计及历史实现记录；下一阶段变更以上述修订方案为准。

## 1. 目标与边界

优先顺序：来敌/清空及时性 → 人员识别 → 当前资料新鲜度 → 全量历史覆盖。
全量指所有实际出现、且经 ESI 确认身份的角色，不扫描 EVE 全部角色。
缓存过期表示需要刷新，不表示删除人员身份。角色 ID 是主键；军团/联盟按 ID 比较，
名称只负责展示。没有联盟必须表示为无联盟，不能把两个空 ID 当成同联盟。

不恢复 zKill 战绩、威胁评分或等级请求；zKill 链接、头像地址由角色 ID 生成。
机器人手动战报分析独立保留。不改变 Presence、OCR 原始上报、事件历史的职责。
档案中不保存“此人当前仍在某星系”作为实时事实，也不永久缓存敌我分类结论。

## 2. 数据模型

生产使用 PostgreSQL 长期档案和有界进程内热点副本，无需新增 Redis。
Gateway 现有可选 PostgreSQL/Redis 请求缓存继续使用，不充当业务活动状态源。

| 表 | 主键/索引 | 数据与规则 |
| --- | --- | --- |
| personnel_profiles | character_id；last_seen_at | 标准姓名、姓名确认时间、组织归属、归属实际获取时间、首次/最近出现、资料版本 |
| personnel_names | name_key | 已确认规范化姓名→角色 ID；active=0 保留失效旧名；冲突不自动覆盖 |
| personnel_organizations | kind + entity_id | 军团/联盟名称及获取时间；长期保存，不固定每 7 天补查 |
| personnel_refresh_jobs | kind + entity_key + context_key；next_due_at | 优先级、下次执行、失败次数、任务版本、租约及本次租约领取版本 |
| personnel_backfill_progress | source | 旧缓存/历史回填游标、导入数及拒绝数，可断点恢复 |

时间使用 UTC 时间戳；姓名索引仅 trim + casefold，不做去标点、压缩内部空格或模糊纠错。
上报原文和历史姓名不改写。明确改名后原子更新当前姓名及新索引，停用原有效索引；
同名映射冲突必须退出事务；实时解析任务保留重试，回填冲突计入 rejected 供管理员核查，不能把其他角色历史迁移过来。

身份和组织归属分别记录获取时间，资料共用修订号：归属结果不能覆盖姓名；组织名称回填也不能把
归属变更误认为刚验证了姓名。旧结果不能覆盖新结果；相同数据同一时间的冲突不得任意胜出。
所有写入必须拒绝无效/非正 ID、非有限时间戳和错误的组织类别。

联系人声望不存入公共档案。继续按授权主体及 contacts 快照版本缓存，只在服务端使用；
后台检查发现授权切换/撤销时先隔离旧快照，再加载新上下文（检查约每 5 个调度周期）。
热读不请求私有 ESI，失败可使用最长 1 小时的同上下文成功快照。军团/联盟名称缺失不阻塞分类。

## 3. 读路径

1. OCR 入站先批量读内存姓名索引，未命中再批量读数据库，数据库读有界，不持全局状态锁。
2. 可信姓名映射命中立即返回角色 ID；资料过期仍可读，后台提升刷新优先级。
3. 完全未知姓名先返回 pending，进入实时队列；视觉来敌和人数不等待 ESI。
4. 姓名解析成功先存身份，再批量刷新归属；组织名称缺失由独立任务补齐。
5. 仅可信成功值长期保存；明确 not_found 短期负缓存。超时/限流/5xx/认证错误不算 not_found。

冷启动只预热当前/近期人员，不把全部档案加载到内存。内存淘汰不删除数据库。
首次识别仍受 ESI 延迟影响；缓存命中后身份读取与组装 P95 <50ms 是待压测目标，
不包含 OCR、网络和 QQ 投递，不作为已经达到的生产指标。

## 4. 字段与人员两维分级

| 级别 | 人员范围 | 归属有效期 / 入队规则 |
| --- | --- | --- |
| P0 | 当前未知身份/映射冲突 | 立即排队 |
| P1 | 当前有效观察中的人员 | 1 小时，到期进入实时队列 |
| P2 | 离开后 24 小时内出现过 | 1 小时，到期进入后台队列 |
| P3 | 最近 1～7 天出现过 | 1 小时，到期进入后台队列 |
| P4 | 最近 7～30 天出现过 | 1 小时，到期进入后台队列 |
| P5 | 超过 30 天未出现 | 1 小时，到期进入后台队列 |

归属期限依据 [官方 OpenAPI](https://esi.evetech.net/meta/openapi.json) 的
`POST /characters/affiliation`：`x-client-cache-ttl`、`x-server-cache-ttl` 均为 3600 秒
（2026-09-11 核对）。这是当前接口策略常量，不是动态解析所有 ESI 接口响应头的通用缓存实现。
P1～P5 只决定处理顺序，不再延长冷资料有效期。到期表示可领取，不是上游限流时仍保证完成的 SLA。
姓名初始 90 天校验一次，
命中不等待校验；资料查询顺带发现改名立即更新。组织名称按 ID 长期复用，新 ID 才补查，
顺带发现改名更新即可。联系人快照初始沿用约 5 分钟，按授权主体而非逐人刷新。
本地黑白名单/规则修改立即提升受影响当前人员的重算任务。

过期身份先用；但过旧的友军归属/声望不能作为屏蔽当前来敌信号的唯一证据。
当前分类归属的缓存有效期与最大信任年龄统一为 1 小时；到期且无其他有效证据时
保留身份展示、分类标为待确认，不根据截图共享图标把每个人都判为敌对。
这个“最大信任年龄”独立于档案保留期，已实现并测试，不沿用无限旧组织友军豁免。

## 5. 调度与资源预算

实时识别与巡检分别保留执行容量，不能仅用一个有优先级的单线程队列。
当前实现：实时 2 个执行槽、后台初始 1 个，后台可增加到 4 个；公共请求共享每秒最多约 5 次的
启动节流及上游退避。槽位/批量上限当前为代码默认值，不是环境变量。依据 CPU 负载、每条数据库
处理耗时、ESI 批次耗时、实时到期积压和退避状态增减，不能仅以 CPU 空闲判断。

- 实时积压或上游退避时，后台停止领取新任务；已在途请求有总超时，不能无限占槽。
- 空闲时增加已到期任务的并发吞吐，不提前官方有效期，也不把冷人员延后 7 天或 30 天。
- 队列持续运行，成功后自动写入下次到期时间，无需新的 OCR 或人工按钮触发下一轮。
- 分页巡检维护所有档案任务；已经落库的多天旧排期会按获取时间加 3600 秒修正。
- 有限批量领取，不把全量档案灌入内存；当前解析/姓名/归属每批最多 100 个实体，上游归属接口上限 1000。
- 不为凑满批次等待实时请求；后台预取分页和内存缓存均有硬上限。
- 同类实体任务只保留一份；再次出现可提升优先级，不能因已有 P5 任务而拒绝 P1。
- 领取使用数据库租约和 SKIP LOCKED；租约到期允许重试，旧租约不能提交资料结果。
- 领取时记录任务版本；任务在执行中被重新请求时，完成旧版本不能消掉新的刷新意图。
- 失败保留成功资料，指数退避并加抖动，尊重 Retry-After；错误日志不能记录令牌或敏感响应。
- 低优先级保留少量领取份额；以最老逾期年龄告警，不能让冷人员无限饿死。

明确未找到负缓存 60 秒，当前不自动延长；请求失败不增加身份否定证据。
全量刷新吞吐量应按唯一人员/组织量、批量大小和可用请求预算估算，不按客户端数估算。

## 6. Gateway 协同与新鲜度

服务端负责“谁活跃/谁先刷新”；Gateway 负责公共请求缓存、合并及上游限流。
`/characters/affiliation/` 返回 character_id、corporation_id、可选 alliance_id/faction_id，
不返回组织名称。分类只需要 ID；遇到新组织 ID 才额外查名称。

Gateway envelope 已兼容新增逐实体 freshness 元数据：fetched_at、expires_at、stale、last_validated_at，
老消费者忽略新增字段；遇到旧 Gateway 不得捏造“刚从 ESI 获取”的时间。
普通内存缓存与可选 ID 缓存均须提供上述时间；普通缓存同一批次的实体共享实际获取时间，
命中、并发合并及过期回退不更新时间，未返回的实体不附加时间。普通缓存重启后为空，
服务端已有获取时间为 0 的档案保留，由当前人员优先的正常刷新修复，不通过清库或伪造时间恢复。
当前不新增客户端强制刷新参数，不绕过共享限流或失败退避；修复网关本地过长 TTL，
不将其等同于必须等待的上游限流期限。
只有真实成功加载/条件验证才更新验证时间，读取旧值不重置其年龄。归属两种网关缓存模式与
服务端均使用官方当前的 3600 秒策略，不受通用 CACHE_TTL 或后台空闲容量影响。
旧的 300 秒/86400 秒归属配置启动时统一为 3600 秒并告警；ID 缓存旧记录按原获取时间
重算有效期和 stale 窗口，不伪造新鲜时间，其他接口的缓存期限不变。
`fetched_at` 表示最近成功从 ESI 获取该响应的时间，并不声称是游戏数据的最后变更时间。
上游 420/429 经 Gateway 映射为 429，并透传经过校验的 Retry-After；服务端不在限流时绕过网关直连。
