# EVE Sentry SSE 重连约束

组织关系/归属短暂过期时，当前事件和 Bootstrap 可带 `personnel_complete=false`。
这不代表人员已确认离开：机器人保存独立的完整名单比较基线，当前查询仍读取当下确认名单，
不把旧名单或旧声望回填成实时结果。待判定完成后，同名单恢复不补发；真实移除仍发更正。
已排队的完整名单等待当前判定完成后继续发送，不能因进入待确认而丢失；视觉清空和
监控失效仍立即取消旧波次的待发名单。旧服务端缺少该字段时保持原来的空名单语义。

本文记录 2026-09-04 的 SSE 首字节阻塞与机器人永久等待问题，防止后续修改重新引入。

生产内嵌模式补充：`app/server/qq_bot_runtime.py` 的 `EmbeddedBotBridge` 不建立事件 SSE，
而是消费服务端进程内的合并唤醒标记，并按 `state:<sequence>` 从持久化事件表读取。下面的
SSE 约束仍适用于独立调试进程、第三方消费者和查询兼容接口；内嵌桥必须保持相同的 ACK、
Bootstrap 对账和单调游标语义。

内嵌桥已有可信基线后，直接分页重放持久化事件，独立于 Bootstrap 刷新。当前态快照在
后台最多保留一个刷新任务；每轮只短暂等待它，刷新慢、未就绪或失败时仍处理来敌、名单
和清空事件。快照水位落后于已确认游标时必须丢弃，不能用旧快照清空新状态。首次启动
没有可信基线时，仍先建立 Bootstrap，避免补播历史。

QQ 发送异常不能结束内嵌消费任务。任务保留已成功写入的 ACK 并退避重试，关闭服务时
必须能中断退避等待。QQ 失败记录 HTTP 状态、官方 `err_code`（兼容旧 `code`）和 trace ID，
不记录令牌、群标识或原始响应正文。

主动群消息共用 Redis 滚动限额：每群每 61 秒最多 20 次请求，机器人合计每 61 秒最多
30 次；多进程、节点通知和 Markdown 降级都共用预算。带 `msg_id` / `event_id` 的被动回复
不占主动预算。官方限流码 `40034100` 或 HTTP 429 按 `Retry-After` 退避，缺省等待 60 秒。
平台另有每天每群 1000 条等权限限额，本地分钟预算不能代替这些权限。

限流后以及积压事件的服务端 `created_at` 超过 60 秒时，QQ 消费者改用新生成、已就绪且
水位不低于已持久化 ACK 的 Bootstrap 对账，只推送当前必要变化，不集中补发旧来敌和清空。
对账成功后才确认快照水位；快照缺失、过期或发送失败时保留 ACK 并继续等待。快照刷新
仍最多一个在途任务，不能因重试重复启动阻塞线程。此策略只适用于 QQ 通知消费者，服务端
持久事件、SSE 重放和计费数据不受影响；事件年龄不能取客户端 `occurred_at`。

依据：[QQ 群消息接口](https://bot.q.qq.com/wiki/develop/api-v2/autogen/api/v2_groups_group_openid_messages.post.html)
及 [接口调用规范](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/api-call-guide.html)。

唤醒标记只是降低延迟的提示。内嵌事件源至多每秒检查一次持久化事件，覆盖标记丢失和
暂时未就绪后的恢复。队列等待本身有截止时间，不能用取消无限期 `to_thread(queue.get)`
来实现轮询，否则会遗留阻塞线程。快照等待超过五秒记录诊断告警，不阻塞已初始化的事件重放。

## 客户端行为

- SSE HTTP 读取必须有有限空闲超时，当前为 45 秒；服务端 heartbeat 为 15 秒。
- 除 HTTPX 的读取超时外，逐行读取也有独立 watchdog。连续没有任何字节时，
  `_stream_once()` 必须退出，让 `run_forever()` 执行退避重连。
- SSE 注释帧（例如 `: connected`、`: keepalive`）表示连接有数据活动，不能当作事件，
  但必须刷新底层读取超时。
- 只有 `id: state:W` 而没有 `data` 的控制块只用于恢复原生 EventSource 游标；机器人解析器
  必须忽略它，不得生成空消息或覆盖尚未处理完成的事件。
- 事件游标只能在事件成功处理后写入 Redis；重连不得跳过未确认事件。
- 服务端当前 wire 事件包括 `bootstrap`、`alert`、`safe` 和 `monitoring_node`；其中
  `alert.data.event_type` 区分内部 `alert.entered` / `alert.updated`，`safe` 对应
  `alert.cleared`，机器人仍需兼容这些内部名称及目标 `node.updated` 映射。
- 机器人成功处理事件后把 `state:<seq>` 保存为 ACK；重连时同时发送该
  `Last-Event-ID` 和单调递增的 Redis 时间游标 `since`。前者保证乱序时间戳不会漏过持久事件，
  后者为没有持久序号的兼容事件提供时间回退，Bootstrap 负责权威状态对账；更旧的序号或
  后续非持久事件 ID 不得覆盖已确认的持久序号。持久序号不能沿用 7 天投递去重 TTL；否则
  安静运行后重连会失去可靠游标。
- `safe`（内部 `alert.cleared`）是服务端持久化的权威清空；服务端不得根据每个连接的前后
  快照临时合成持久清空。机器人若漏收 `safe`，可用权威 Bootstrap 的星系差集做一次幂等
  对账并发送补偿清空，不能把每次重连都当作新的清空事件。
- Bootstrap 已经把某星系校准为空后，随后到达的同一持久清空事件只做确认，不得再次推送
  清空消息；Redis 时间游标只能单调前进，迟到事件不得将它倒退。

## 节点快照

`process_bootstrap()` 的初始节点快照有版本和 Redis 去重保护。不要把“连接重建”
简单改成每次都强制推送完整节点列表；只有首次初始化、版本变化或 Redis 状态丢失时才允许
触发完整快照。

## 服务端配合

服务端必须在返回 SSE 响应头后尽快发送至少一个字节，并保证 heartbeat 间隔小于客户端
空闲超时。服务端以数据库一致快照水位 `W` 为边界，先完整重放 `seq <= W` 的持久状态事件，
再发送 `state:W` Bootstrap；快照未就绪、落后于事件或落后于客户端游标时不得用空状态或
旧状态替代。客户端不能依赖服务端永远保持连接，也不能用永久阻塞替代对账机制。
